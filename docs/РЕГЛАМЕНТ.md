## 1. Что требуется сделать (постановка задачи, стр. 6)

Разработать чат-бота или мини-приложение на Платформе для бизнеса в MAX, решающее актуальную задачу бизнеса, с практической ценностью для конкретной аудитории. Онлайн-этап = MVP:
1. целевая аудитория и приоритетный сегмент — с обоснованием;
2. конкретная проблема пользователя — с подтверждением актуальности;
3. UX и основной сценарий (начало → действия → результат);
4. MVP — чат-бот или мини-приложение, **на выданном токене**;
5. потенциал масштабирования и условия внедрения;
6. ожидаемый эффект и показатели, по которым его можно проверить;
7. презентация.

Офлайн-этап (финал): сценарий пилота и внедрения, доработка, демонстрация, защита.

Аннотация трека: «от поиска сотрудников и работы с документами до получения мер поддержки, взаимодействия с клиентами и организации других бизнес-процессов». Модели B2C, B2B, B2G — любые. Направления, обозначенные ведомствами (стр. 5): навигация по мерам поддержки; цифровое сопровождение документов и разрешений; контроль и надзор без лишней нагрузки; кадры для бизнеса и сельского хозяйства; импорт/экспорт и промкооперация. Они «задают отраслевой контекст, но не ограничивают выбор проблемы».

Прямые сигналы организаторов (стр. 16): «Не начинайте с формулировки "создадим AI-ассистента", "сделаем навигатор" или "разработаем агрегатор"». Ищите ситуации, где информация разбросана по источникам, порядок действий зависит от региона/статуса, ошибка на одном этапе ломает процесс, один процесс требует нескольких участников, между существующими сервисами остаются ручные переходы.

## 2. Ограничения (стр. 7) — своими словами

1. Решение — по теме трека, для предпринимателей/компаний, актуальность обоснована.
2. MAX — среда реализации и/или взаимодействия; основной сценарий проверяется **в MAX**.
3. Должно работать и в мобильной, и в веб-версии MAX.
4. Рекомендуют JavaScript и React; другие языки допустимы.
5. Форматы: чат-бот; чат-бот + мини-приложение. **Мини-приложение подключается к боту и не является изолированным сервисом.**
6. Собственный API — не обязателен и баллов сам по себе не даёт.
7. Запрещены закрытые библиотеки, частные API и чужой код без свободной лицензии.
8. Никаких токенов/паролей/ключей в репозитории.
9. Соблюдать законодательство РФ, правила платформы MAX и правила хакатона.
10. Если вместо реальной интеграции — тестовые/смоделированные данные, это **явно указывается в материалах**.
11. Ник чат-бота после создания изменить нельзя.
12. После дедлайна код не меняется (до объявления результатов онлайн-этапа).

## 3. Формат сдачи (стр. 9–10)

Обязательно:
1. Работающее решение в MAX — ссылка/способ доступа для прохождения основного сценария.
2. Git-репозиторий с commit hash (или архив с контрольной суммой). После дедлайна — заморозка.
3. `README.md`: назначение; основной сценарий; состав и архитектура; **одна команда запуска через Docker**; параметры окружения; переменные; порты; зависимости; внешние сервисы и интеграции; работа с данными; порядок работы с тестовыми данными; пошаговый сценарий проверки; примеры ожидаемого поведения; известные ограничения; остановка и перезапуск. Внешний сервис, который нельзя воспроизвести в Docker, — описать отдельно (назначение, условия проверки).
4. Файл зависимостей с зафиксированными версиями.
5. Docker: `Dockerfile`, `compose.yaml`/`docker-compose.yml` (всё одной командой), `.dockerignore`, `.env.example` без секретов. **Сборка ≤ 5 минут** (без учёта скачивания базовых образов). Готовый образ в Docker Hub — можно, но не вместо исходников.
6. Презентация PDF. **Первый слайд — служебный**: ссылка на бота/мини-приложение; репозиторий + commit hash; адрес собственного API (если есть); тестовые логины/пароли; рабочие токены и переменные окружения для запуска и проверки; краткий порядок прохождения сценария. Со второго слайда: название и команда; executive summary; ЦА, проблема, актуальность; решение и основной сценарий; ожидаемый эффект; архитектура; данные и интеграции; масштабирование и условия адаптации; ограничения, риски, допущения; источники.

Только для решений с собственным API: HTTPS-адрес на период проверки; `openapi.yaml` (3.0/3.1); тестовые учётные записи по ролям; тестовые данные (JSON/CSV); `DATA-API.yaml` (версия схемы, имя решения/ID команды, базовый адрес, перечень обязательных проверок, метод + путь, параметры, роль, ожидаемые коды, формат ответа).

## 4. Критерии оценки (стр. 11–14)

Шкала 0–3 на критерий (0 — не выполнен / нельзя оценить; 1 — слабо; 2 — частично; 3 — хорошо).

**Допуск (0 баллов и дальше не оценивают):** не по теме / не про MAX; бот или мини-приложение не запускается или основной сценарий нельзя пройти; нет презентации.

**Продуктовая часть — 40%:**
| Вес | Критерий | Что смотрят |
|---|---|---|
| 35% | Потенциал масштабирования | конкретные контексты/регионы/организации помимо исходного кейса; направления соответствуют логике продукта; условия адаптации (данные, интеграции, ресурсы, изменения); ограничения и риски; реалистичный порядок тиражирования |
| 25% | Пользовательская ценность | чёткая ЦА и сегмент; конкретная потребность; сформулированный результат; преимущество перед текущим способом; подтверждение данными/наблюдениями/допущениями |
| 20% | UX/UI | путь соответствует сценарию; понятно без пояснений; действия легко найти; интерфейс сообщает о загрузке/результате/ошибке; нет лишних шагов и тупиков |
| 15% | Обоснованность и целостность | решение ↔ проблема; логическая связь проблема → механика → эффект; аргументированные решения; функции согласованы; реалистично |
| 5% | Презентация | структура, ясность, достаточность, читаемость, без перегруза |

**Техническая часть — 60%:**
| Вес | Критерий | Что смотрят |
|---|---|---|
| 30% | Работоспособность и полнота | основной сценарий проходится от начала до результата; ключевые функции работают; для API — проверки проходят |
| 20% | Интеграция и обмен данными | компоненты взаимодействуют корректно; данные/состояния передаются предсказуемо; внешние интеграции работают как заявлено; для API — коды/форматы соответствуют контракту |
| 20% | Реализация и архитектура | структура соответствует MVP; понятны компоненты и связи; логика разделена и поддерживаема; технологии соответствуют функциональности |
| 10% | Стабильность и ошибки | стабильно при повторном прохождении; ошибки пользователя обрабатываются; после ошибки можно продолжить без перезапуска; нет тайм-аутов и критических задержек |
| 10% | Безопасность и данные | нет секретов в коде; зависимости зафиксированы; доступ к данным соответствует логике; внешние сервисы описаны; нет очевидных рисков |
| 10% | Документация и комплектность | материалы соответствуют версии; воспроизводимо по инструкции; описаны запуск/архитектура/зависимости/окружение/интеграции; порядок проверки; ограничения |

**Платформенный бонус +0,15 (целиком или никак; только онлайн-этап):** основной сценарий полностью работает; использована возможность MAX сверх минимума; она создаёт пользовательскую ценность, органично встроена, работает от начала до результата и описана в материалах. Собственный API и «много функций» — не основание.

**Финал (для планирования, стр. 14):** техоценка продукта 40% + защита 60%. Защита: ценность и соответствие 25%; масштабирование и тиражирование 25% (регионы/организации, что сохраняется/адаптируется, данные/интеграции/участники, риски, путь от пилота); качество MVP и UX 20%; сценарий запуска и внедрения 15% (первый регион/сегмент, встраивание в процессы, участники, каналы доступа, метрики пилота); качество защиты 10%; командное владение 5% (роли, каждый владеет своей зоной — **на финале команда из одного человека будет заметна**, это надо закрыть подготовкой Александры и Павла хотя бы к ответам по своим «зонам»).

## 5. Методические подсказки организаторов, которые надо отразить в SPEC.md

- Формула проблемы: «[Пользователь] в ситуации [контекст] хочет [результат], но сталкивается с [барьером], из-за чего [последствие]» + проверка: кто пользователь, какая задача, где в процессе проблема, почему значима, чем подтверждается.
- As Is / To Be по шагам; не автоматизировать весь путь — найти одну точку максимального эффекта.
- Гипотеза: «Если мы поможем [пользователю] выполнить [действие] с помощью [механики], [результат] станет [лучше], потому что [обоснование]» + хотя бы один измеримый показатель (время процесса, число ручных действий, ошибки, доля завершивших, повторные обращения).
- MoSCoW с обязательным **Won't Have** («ограничение объёма — часть сильного продуктового решения»).
- Работа с официальными данными: первоисточник; актуальность и территория; разделять факт / расчёт / рекомендацию / допущение; **не имитировать интеграции**; LLM — только с привязкой к источникам, не выдавать предположение за факт.
- Масштабирование = ядро (проблема, логика сценария, архитектура, модель данных, механика, ключевые элементы UI) vs переменная часть (региональные данные, нормативка, справочники, внешние системы, интеграции, роли, бизнес-правила) + ответы: где ещё есть такая проблема, куда масштабировать первым делом, что переносится без изменений, что адаптировать, какие данные/интеграции/ресурсы, риски, следующий шаг.
- Пилот: для кого и где; как встраивается в процесс; данные/интеграции/участники; как пользователи получат доступ; метрики; следующий шаг.
- Источники, рекомендованные организаторами: реестр МСП (ФНС), МСП.РФ, портал КНД, «Работа России», «Мой экспорт» (РЭЦ), реестры Росаккредитации, ГИСП.
- Стек: Bot API, конструкторы сценариев, MAX Bridge, MAX UI (React); мини-приложение — HTML/JS/CSS по HTTPS. «Перед началом разработки и перед сдачей обязательно сверяйтесь с актуальной документацией и историей изменений API».
- Когда мини-приложение оправдано: сложная форма, много параметров, сравнение объектов, список/каталог, возврат к введённым данным, несколько связанных элементов одновременно, сложный визуальный интерфейс. Чат-бот — для последовательных вопросов, выбора из нескольких опций, персонального результата, проверки статуса, уведомлений, регулярного короткого действия.
