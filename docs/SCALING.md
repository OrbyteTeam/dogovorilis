Версия 1.0 · 20.09.2026 · «Договорились», команда Pulsar. Критерий жюри: «Потенциал масштабирования» — 35 % продуктовой
оценки (онлайн-этап) и 25 % защиты (финал). Жюри смотрит: конкретные контексты/регионы/организации помимо исходного
кейса; соответствие направлений логике продукта; условия адаптации (данные, интеграции, ресурсы, изменения);

## 1. Ядро продукта и переменная часть

Ядро — то, что не меняется при переносе в любой контекст (по методичке организаторов: проблема, логика сценария,
архитектура, модель данных, механика взаимодействия, ключевые элементы интерфейса):

| Ядро | Что именно |
|---|---|
| Проблема | договорённость между двумя сторонами, сложившаяся в переписке, не имеет подтверждения, привязки к оплате и документального закрытия |
| Логика сценария | условия → подтверждение второй стороной → платёж по событию (предоплата / приёмка) → документы → напоминания |
| Архитектура | бот + мини-приложение в MAX, машина состояний сделки, карточка «у обеих сторон», планировщик напоминаний, PDF, слой рейлов оплаты |
| Модель данных | сделка · версии условий · платежи · события · напоминания · чек (`server/migrations/0001_init.sql`) |
| Механика | второй участник приходит по диплинку из существующего чата; подтверждение — кнопкой; статус обновляется на месте |
| Ключевой UI | карточка сделки, форма «что/когда/сколько/предоплата/правило отмены», кнопки «Подтверждаю / Предложить изменения» |

Переменная часть — то, что меняется при тиражировании:

| Переменная | Значения в пилоте | Во что превращается при масштабировании |
|---|---|---|
| Шаблоны ниш | красота, занятие, ремонт, на заказ, работа под ключ | отраслевые наборы полей и правил (этапы для ремонта, партии для фермера, слоты для аренды) — данные, не код |
| Режим чека | НПД (самозанятый), ИП с кассой, без чека | партнёрское автоформирование чека НПД через оператора (Bank 131, Qugo, Наймикс, Prodamus) ; фискализация ИП через эквайринг с 54-ФЗ («Чеки от ЮKassa», Атол) |
| Рейл оплаты | ссылка эквайринга (тест), перевод по реквизитам | СБП-QR банка исполнителя (Т-Бизнес, Точка, Альфа — у всех есть API счетов/ссылок [П]); универсальный платёжный код НСПК (УПК) → цифровой рубль; нативная оплата по QR НСПК внутри MAX (анонс 04.06.2026 [П]) |
| Правила отмены / предоплаты | 4 правила | справочник по отрасли и региону (например, обязательная предоплата 50 % для изделий на заказ) |
| Роли | исполнитель ↔ клиент | заказчик ↔ исполнитель (микро-B2B), фермер ↔ закупщик, арендодатель ↔ арендатор, бригадир ↔ работник |
| Документы | квитанция PDF, чек-вложение | акт оказанных услуг с полями по 402-ФЗ, УПД для B2B, спецификация партии для АПК — шаблоны |
| Подпись стороны | кнопка + MAX id (+ телефон HMAC) | Цифровой ID MAX для организаций/ИП (API доступен ЮЛ/ИП [П]), ПЭП по соглашению сторон, в перспективе УКЭП через операторов ЭДО |
| Язык/локаль | русский, МСК | `user_locale` из событий MAX. Время в БД хранится в UTC, но **интерфейс сейчас показывает время по Москве** с меткой «(МСК)»; пояс сделки (поле `timezone` у сделки и профиля, выбор в форме) — отдельный этап перед выходом за пределы МСК-региона |
| Каналы привлечения | сообщества самозанятых, центры «Мой бизнес» | банки-партнёры MAX, МСП.РФ, отраслевые ассоциации, платформа партнёров MAX (каталог мини-приложений) |

## 2. Куда масштабировать в первую очередь и почему

Порядок — по близости к ядру и по готовности «второго участника» быть в MAX.

### Этап 0 — пилот (онлайн-этап + 2 месяца после)
**Сегмент:** самозанятые сферы услуг с клиентом-физлицом: мастера красоты на дому, репетиторы, ремонт техники/квартир,
фотографы, кондитеры/флористы на заказ. Крупнейшие категории самозанятых — ремонт (977 тыс.) и красота (484 тыс.) [П];
средний чек ≈ 1,3 тыс. ₽, 227 млн чеков/мес (ФНС, авг. 2026) [П].
**Регион:** Москва и Московская область (2,4 млн самозанятых, средний чек 2 852 ₽ [П]) — плотность и доступ команды к
респондентам; параллельно Казань/Татарстан как площадка финала (финал 29.10.2026 на Kazan Digital Week).
**Канал:** сообщества самозанятых в MAX и Telegram (мастера, репетиторы), центры «Мой бизнес» (у них программы для
самозанятых), сарафан через самих клиентов (каждая карточка — приглашение в продукт).
**Встраивание в процесс:** ничего не меняется в том, как мастер общается — он добавляет ссылку в существующий чат.
**Метрики пилота:** ≥ 30 исполнителей, ≥ 200 сделок; доля сделок с подтверждением клиента ≥ 60 %; доля с предоплатой ≥ 40 %;
no-show до/после (самоотчёт); медиана «создана → предоплата» ≤ 6 ч; доля оплат с чеком до 9-го ≥ 90 %; NPS исполнителей.
**Следующий шаг после пилота:** партнёрство с одним оператором чеков НПД (автоформирование чека по событию `payment.succeeded`)
и одним банком для СБП-ссылок исполнителей — это снимает две «модели» из MVP.

### Этап 1 — ИП с кассой и микро-B2B (квартал после пилота)
**Что переносится без изменений:** вся машина состояний, карточка, напоминания, PDF, демо-режим, рейлы.
**Что адаптируется:** режим чека `ip_kkt` — чек 54-ФЗ формирует эквайринг («Чеки от ЮKassa» / Атол Онлайн) по событию
оплаты; появляется документ «Акт» (реквизиты сторон: ИНН, адрес — из профиля, для ИП — из реестра МСП ФНС, открытые данные [П]);
шаблон «этапы» (несколько платежей внутри сделки — ремонт, разработка). Роли те же.
**Данные и интеграции:** реестр МСП ФНС (XML, открыт) для реквизитов; API «выставление счёта» банка ИП (Т-Бизнес, Точка [П]) как
рейл вместо эквайринга-агрегатора; ЭДО — не нужен (акт подписывается ПЭП сторон в MAX по соглашению).
**Регионы:** любые — ничего регионального.
**Риск:** конверсия клиента-ИП в «Подтверждаю» ниже (у B2B есть договоры); снижаем шаблоном «счёт-договор» с основанием.

### Этап 2 — отраслевые вертикали с региональной спецификой (полгода)
Здесь ядро то же, меняются шаблоны и справочники, и появляется «казанский» сюжет.
1. **АПК: партия фермера → магазин/кооператив** (Татарстан: 3 132 КФХ, 417 тыс. подворий; ПФО — лидер по делам Россельхознадзора [П]).
   Сделка = партия: объём, цена, дата отгрузки, документы (номер ВСД «Меркурий», коды маркировки) как вложения/поля;
   напоминания о гашении ВСД в 1 рабочий день. Интеграция с Ветис.API — по заявке (тестовый контур) — этап после пилота; до этого
   номера ВСД вводятся вручную. Второй участник — закупщик (магазин, кооператив) — в MAX через бизнес-платформу.
2. **Сезонные бригады (кадры для АПК/стройки/HoReCa):** сделка = наряд на смену/период: ставка, часы, объект; подтверждение
   выхода и отметка по геометке/QR (`request_geo_location`, `openCodeReader` — обе возможности в MAX [П]); расчёт к выплате + чек
   исполнителя. Регионы: Краснодар (11,2 тыс. вакансий АПК), Татарстан (1 000+ студентов в аграрных отрядах, 3 400 подростков за лето
   2026), Башкортостан, Ставрополь [П].
3. **Аренда и услуги с залогом** (аренда оборудования, помещений посуточно): сделка = бронь с депозитом, правило отмены,
   приёмка с фото. Нужен только новый шаблон.
Что адаптируется: шаблоны, справочники (регионы, отрасли, документы), правила предоплаты; интеграции — по одной на вертикаль.
Что не меняется: код машины состояний, карточка, рейлы, напоминания, PDF.

### Этап 3 — платформенный уровень (год)
- **Каталог мини-приложений MAX / платформа партнёров:** «Договорились» как встроенная возможность бизнес-аккаунта: любая
  компания на business.max.ru получает «карточку договорённости» для чатов с клиентами (> 500 тыс. компаний в платформе [П]).
- **Банки-партнёры MAX** (ВТБ, Альфа, Т-Банк — все с продуктами для самозанятых): карточка сделки как «умный запрос оплаты» в их
  мини-приложениях; для нас — рейлы без агрегатора.
- **Госсегмент:** центры «Мой бизнес» и МСП.РФ (раздел самозанятых) — обучение и раздача шаблонов; регионы с программами
  поддержки самозанятых (Москва, Татарстан, Башкортостан) как первые организации-партнёры.

## 3. Условия адаптации — что потребуется на каждом переходе

| Переход | Данные | Интеграции | Ресурсы | Изменения продукта |

| Пилот → ИП | реестр МСП ФНС (открытые данные) | эквайринг с фискализацией; API счетов банка | 1 разработчик, 1 месяц | режим чека, акт, этапы |

| → бригады | ОКПДТР, нормы ТК для 14–18 лет | «Работа России» (opendata API) — опционально | бригадир-партнёр, 1 КФХ | шаблон «наряд», гео/QR-отметка, ведомость |
| → платформа партнёров | — | Цифровой ID (ЮЛ/ИП), API бизнес-платформы MAX | соглашение с ООО «МАХ» | мультиаккаунт организации, роли сотрудников |
| → цифровой рубль / смарт-контракты | тарифы ЦБ (0 % в 2026, 0,3 % с 2027 [П]) | УПК через банк исполнителя; ПКСК Банка России (концепция 18.06.2026 [П]) | банк-участник платформы ЦР | «сделка» как шаблон условного платежа: событие «принято» → перевод |

## 4. Что переносится без изменений, что адаптируется (сводка для слайда)

**Без изменений:** проблема и сценарий; машина состояний (12 статусов, 17 переходов); карточка у обеих сторон и механика
диплинка; планировщик напоминаний; квитанция PDF; двойной рейл с ручным подтверждением как запасной; демо-режим; код и Docker.
**Адаптируется данными (без кода):** шаблоны ниш, правила отмены/предоплаты, тексты, документы-шаблоны.
**Адаптируется кодом (модуль на вертикаль):** рейл оплаты (провайдер), режим чека (оператор), документы (акт/УПД/спецификация),
источник реквизитов (реестр МСП, Цифровой ID), отраслевые интеграции (Ветис, ЧЗ).

## 6. Технические условия масштабирования

**Где упрёмся и что делаем.** Расчёт на цель «100 тысяч сделок в день» [Д]: ~5 напоминаний на сделку →
500 тыс. в сутки ≈ 21 тыс. в час; ~15 сообщений MAX на сделку (карточки, правки, уведомления) ≈ 17 запросов в
секунду в среднем и кратно больше в пиках.

| Узкое место | Предел сейчас | Что делаем | Когда |
|---|---|---|---|
| Планировщик напоминаний | один процесс, 50 напоминаний за тик 30 с ≈ 6 тыс./час | выборка уже на `FOR UPDATE SKIP LOCKED` → N воркеров без изменения схемы; тик и батч — параметры | > 10 тыс. сделок/день |
| Отправка в MAX | лимит платформы 30 rps на токен и 2 сообщения/с в один чат; очередь — в памяти процесса | outbox-таблица сообщений + отдельный воркер отправки с троттлингом и ретраями; при росте — несколько ботов/бизнес-аккаунтов с шардированием по исполнителю | > 30 тыс. сделок/день |
| Rate-limit и троттлинг | в памяти одного процесса | перенос счётчиков в Postgres/Redis, когда процессов станет больше одного | вместе с N воркерами |
| Рейл «ссылка» | один тестовый магазин команды (`YOOKASSA_SHOP_ID` глобальный) | эквайринг **исполнителя**: ключи магазина/банка в `seller_profiles.acquiring`, вебхук с маршрутизацией по магазину | до первых платящих пользователей (этап 0) |
| Рост таблиц `deals` / `deal_events` / `reminders` | одна БД, индексы на месте | партиционирование `deal_events` и `reminders` по месяцу, архив закрытых сделок старше года | > 50 млн событий |
| HTTP (мини-приложение, вебхуки) | один процесс Fastify | горизонтально за балансировщиком — состояние уже в БД (ожидание ввода, карточки, платежи) | по нагрузке |
| Хостинг | один VPS 2 × 3,3 ГГц / 4 ГБ | управляемый Postgres с репликой, 2+ узла приложения, бэкапы вне узла | этап 1 |

До ~10 тыс. активных сделок в день ничего менять не нужно [Д]: слои уже разделены (транспорт / домен / данные /
интеграции), поэтому планировщик и вебхуки выносятся в отдельные процессы без переписывания логики.
Webhook-режим MAX на VPS (HTTPS, Let's Encrypt) — уже в compose (`--profile prod`).

**Не маркетплейс и не эскроу.** Масштабирование не превращает продукт в посредника: платформа не принимает, не
держит и не распределяет деньги (не платёжный агент по 103-ФЗ), не выбивает чеки за исполнителя (54-ФЗ/422-ФЗ
остаются на нём) и не ищет клиентов. Растём числом исполнителей и сделок, а не оборотом через свой счёт —
поэтому масштаб не требует лицензий и резервов под чужие деньги.

**ООО и B2B.** Для ИП и ООО добавляется документ «Акт/УПД» к той же сделке (реквизиты — из профиля и реестра МСП),
подпись сторон — через Цифровой ID MAX, когда он станет доступен ботам; до этого — подтверждение кнопкой с
фиксацией версии условий, как сейчас. Мультиаккаунт организации: `seller_profiles` расширяется до «организация →
сотрудники» без изменения `deals`.

**Расписание исполнителя (ЗАДАЧА_08 D, следующий шаг).** Сейчас клиент выбирает время по сетке 08:00–21:30 с шагом
30 минут, а занятость считается из договорённых сделок исполнителя с их длительностью. Следующий шаг — **настройка
рабочих часов и перерывов** исполнителя (дни недели, часы, выходные), затем буфер между визитами. Полноценные слоты,
ресурсы и онлайн-запись незнакомцев — сознательно не наш путь: это территория систем записи (YCLIENTS и др.), а
продукт остаётся договорённостью между исполнителем и клиентом, который его уже знает.

**Варианты в карточке (ЗАДАЧА_08 C, вторая очередь).** Исполнитель кладёт в карточку до трёх своих услуг, клиент
выбирает одну кнопкой, выбор становится новой версией условий и подтверждается как обычно. Это по-прежнему не витрина:
варианты выбирает исполнитель для конкретного клиента.

**Надёжность исполнителя (ЗАДАЧА_08 E).** Показатели считаются из фактов сделок при каждой загрузке, если исполнитель
показывает их клиентам. При тысячах сделок у исполнителя — материализованные счётчики в `seller_profiles`,
обновляемые на переходах T15/T16 (та же транзакция), и пересчёт раз в сутки для сверки.

**Проверка чека.** Сейчас чек — файл, приложенный исполнителем, содержимое не проверяется. Следующий шаг —
чтение QR чека ФНС (`openCodeReader` в мини-приложении) и проверка реквизитов чека по сумме и дате оплаты.

## 7. «Когда платформа запустит X, мы получаем Y» — платформенный риск как преимущество

## 8. Риски масштабирования и как их снимаем

| Риск | Вероятность | Мера |
|---|---|---|
| Клиенты не нажимают «Подтверждаю» (трение) | средняя | клиент получает выгоду: понятные условия, напоминание, чек и квитанция; кнопка — одна; текст приглашения от имени мастера |
| Самозанятые «в серую» не хотят фиксации | средняя | пилот — на тех, кто уже платит НПД (17 млн); аргумент — защита от «оплатил/не оплатил» и от штрафа за чек |
| Провайдер платежей меняет условия (как ЮKassa отключила чеки СМЗ с 29.12.2025) | высокая | рейл — сменный модуль; ручной рейл всегда доступен |
| Платформа сделает «запрос оплаты» сама | средняя | мы выше по стеку: договорённость и закрытие документами; см. §7 |
| Регуляторный: платёжный агент (103-ФЗ) | низкая при нашей архитектуре | деньги идут напрямую исполнителю; продукт не принимает средства |
| Зависимость от MAX Bot API (лимиты, изменения) | средняя | троттлинг, сверка с changelog перед сдачей (правило регламента), SDK официальный |
| Юридическая сила подтверждения в чате | средняя | подтверждение + MAX id + телефон HMAC + квитанция — это переписка с существенными условиями (доказательство в суде, как в кейсах из `../research/user_pains.md`), а не замена договора; в B2B — ПЭП по соглашению |

## 10. Юнит-экономика (эскиз, все цифры — допущения)
Стоимость: инфраструктура ≈ 1–2 тыс. ₽/мес на 1 000 активных исполнителей; поддержка — общая. Монетизация — не в MVP;
возможные модели: бесплатно для самозанятых (охват), подписка для ИП/организаций (шаблоны, акты, сотрудники), партнёрская
комиссия банков за приведённый оборот по СБП. Продукт остаётся полезным без монетизации — как инфраструктура доверия в MAX.
