## 1. Продукт в одном абзаце

**Договорились** — бот и мини-приложение в MAX, где самозанятый или микро-ИП фиксирует договорённость с клиентом
(что / когда / сколько / предоплата / правило отмены) одной карточкой, клиент подтверждает её кнопкой в чате,
предоплата и остаток проходят по выбранному рейлу (ссылка эквайринга или перевод), статус обновляется
у обеих сторон в одном и том же сообщении, бот сам напоминает о визите, оплате и чеке, а по завершении обе
стороны получают чек и квитанцию о сделке PDF. Мы не касаемся денег: платёж идёт напрямую исполнителю.

**Актуальность (для презентации и README):**
- 17,26 млн самозанятых, 227,5 млн чеков в месяц (ФНС, авг. 2026); самозанятым открыли бизнес-платформу MAX
  15.06.2026; 57 % МСБ ведут дела «в мессенджерах и заметках», CRM — у 27 % (МТС/Авито, дек. 2025).
- No-show по записи 18–20 % (YCLIENTS/ProDoctorov); предоплата снижает его на 40–60 %; 31 % МСБ с существенной
  просроченной дебиторкой (ПСБ/НАФИ, дек. 2025); ЮKassa отключила чеки самозанятым с 29.12.2025.
- Реальный кейс из MAX: «Есть скрины переписки в Максе, что работа выполнена и клиент её принял» — долг 131 650 ₽
  (ИП по ремонту оборудования, Правовед.ru, 2026). Скрин ≠ подтверждённая договорённость.
- **Смарт-контракты:** Банк России 18.06.2026 опубликовал концепцию «Платформы коммерческих смарт-контрактов
  в цифровых рублях» — «программы, которые автоматически выполняют условия сделки при наступлении заранее
  определённых событий»; предложения принимаются до 30.09.2026 (https://cbr.ru/press/event/?id=32630).
  Карточка «условия → подтверждение → событие (приёмка) → оплата» — это прообраз условного платежа для
  микробизнеса без блокчейна; когда ПКСК откроется рынку, наша сделка становится шаблоном смарт-контракта
  (см. `docs/SCALING.md` §7).
Источники со ссылками — `../research/user_pains.md`, `../research/invoicing_audit.md`, `../research/context_max_payments.md`.

## 2. Пользователи, проблема, истории

**Сегмент пилота:** самозанятые и микро-ИП сферы услуг, договаривающиеся с клиентом в переписке: мастера красоты
на дому, репетиторы, ремонт техники/квартир, фотографы, кондитеры и флористы на заказ, фриланс. Клиент — физлицо
(иногда ИП). Обе стороны уже в MAX.

**Проблема:** Самозанятый мастер, когда договорённость с клиентом сложилась в переписке MAX, хочет получить
предоплату/оплату вовремя, не потерять слот и закрыть сделку чеком без штрафа, но условия размазаны по чату,
предоплату неловко просить и негде связать с записью, статус оплаты видит только он, а чек — ручное действие
в другом приложении с дедлайном «до 9-го», из-за чего no-show, споры «вы обещали другую цену / оплатил — не
оплатил», штраф 20 %/100 % за чек и потерянный доход.

**User stories, которые обязан закрывать MVP** (дословные цитаты — `../research/user_pains.md`, коды A1…E3):
1. (A1, A2) Мастер маникюра: запись подтверждается предоплатой с понятным правилом отмены, просить не приходится —
   правило живёт в карточке.
2. (A3) ИП по ремонту: изменение цены по ходу работ фиксируется новой версией карточки с подтверждением клиента.
3. (A4–A6) Репетитор: правило отмены и статус оплаты видны обеим сторонам; напоминает бот, а не человек.
4. (B3) Самозанятая: напоминание сформировать чек именно по этому поступлению до 9-го числа.
5. (A10, B12) Клиент: видит, на что договорились, статус и получает чек и квитанцию в тот же чат.
6. (E1, E2) Кондитер: макет/фото, вес, дата и сумма подтверждены одной кнопкой; выдача зафиксирована.

**Гипотеза и метрики:** если мастер фиксирует договорённость и предоплату одной карточкой с подтверждением
клиента, то доля сорванных записей снижается, время «договорились → оплачено» сокращается, доля оплат с чеком
в срок растёт. Метрики пилота: доля сделок с подтверждением; доля с предоплатой; no-show до/после; медиана часов
«создана → предоплата»; доля оплат с чеком до 9-го; число споров, разрешённых по карточке.

## 3. Роли и глоссарий

| Термин | Значение |
|---|---|
| Исполнитель (seller) | пользователь MAX, создавший сделку. Любой пользователь может быть исполнителем; отдельной регистрации нет |
| Клиент (client) | пользователь MAX, открывший ссылку сделки. В одной сделке ровно один клиент |
| Сделка (deal) | объект с версиями условий, платежами, событиями и статусом (§5) |
| Версия (version) | снимок условий: название, описание, дата, сумма, предоплата, правило отмены, фото. Подтверждается клиентом целиком |
| Карточка (card) | сообщение бота с текущим состоянием сделки и кнопками, своё у каждой стороны; обновляется на месте |
| Рейл (rail) | способ оплаты: `link` — ссылка эквайринга (провайдер ЮKassa **[тест]** или Т-Банк СБП **[тест]**); `transfer` — перевод по реквизитам исполнителя с ручным подтверждением обеих сторон **[модель]** |
| Квитанция (receipt PDF) | документ о сделке, который бот формирует сам (§11). Не фискальный чек |
| Чек | фискальный документ, который исполнитель формирует вне продукта («Мой налог» или касса) и прикладывает к сделке |
| Демо-режим | «Открыть как клиент»: исполнитель проходит клиентскую сторону в своём же чате (§12) |

## 4. Архитектура

### 4.1. Компоненты

Один процесс Node.js (бот + HTTP + планировщик) и одна БД. Второго процесса нет намеренно: проще запуск одной
командой, меньше точек отказа. Горизонтальное масштабирование — не цель MVP (см. SCALING §6).

### 4.4. Последовательность старта
1. `config.ts` валидирует env; при ошибке — понятное сообщение и `exit(1)`.
2. Подключение к БД с ретраем (10 попыток × 3 с) — compose ждёт `db` healthy, но ретрай всё равно нужен.
3. Миграции (`server/migrations/*.sql` по алфавиту, таблица `schema_migrations`, каждая в транзакции).
4. HTTP-сервер (Fastify) слушает `PORT`: `/healthz`, `/readyz`, `/api/*`, `/webhooks/*`, `/pay/return`, `/app/*`.
5. Бот (если `MAX_MODE != off`): `botInfo = await api.getMyInfo()` → `MAX_BOT_USERNAME` (env или `botInfo.username`);
   `setMyCommands` (§6.1); затем:
   - `polling`: `bot.start({ mode: 'polling', options: { allowedUpdates: [...] } })` — **внимание: SDK удаляет все
     webhook-подписки этого токена** (CONTRACTS §1.3). Поэтому один токен = один работающий экземпляр.
   - `webhook`: `bot.webhookCallback({ domain: PUBLIC_BASE_URL host, path: '/webhooks/max', secret })` — обработчик
     **без подписки** — регистрируется в Fastify как raw-handler (`POST /webhooks/max`); подписка
     (`bot.api.subscribe(url, secret, allowedUpdates)`, чужие подписки токена снимаются) — только **после**
     `app.listen` (п. 4 ↔ 5), иначе первые доставки MAX получают 502. Порт наружу — 443 через Caddy.
     Не использовать `startWebhook` (он поднимает второй http-сервер). Сторож в планировщике раз в 5 минут
     возвращает подписку, если её сняли (чужой polling, MAX через 8 ч); `/readyz` показывает `subscription`.
   - Ошибка `fetch failed` с `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`/`SELF_SIGNED_CERT_IN_CHAIN` → лог с подсказкой
     про `certs/russian_trusted_bundle.pem` и `exit(1)`.
   - `allowedUpdates`: `bot_started`, `message_created`, `message_callback`, `bot_stopped`, `dialog_cleared`.
6. Планировщик: `setInterval` 30 с; задания §10 и §9.6; защита от наложения (флаг «выполняется»).
7. Graceful shutdown: SIGTERM → остановить планировщик и polling, дождаться текущих запросов (≤ 10 с), закрыть pool.
   Webhook-подписку MAX **не снимать**: рестарт не должен оставлять бота глухим.

### 4.5. Логи и наблюдаемость
pino JSON; каждый входящий update/запрос — `request_id`; в логах никогда нет токена, `initData`, реквизитов,
секретов провайдеров (маскировать). Ошибки интеграций — уровень `warn` с `provider`, `op`, `status`, `code`.
`/healthz` — процесс жив; `/readyz` — БД отвечает и (если `MAX_MODE != off`) бот инициализирован; в режиме `webhook`
ещё поле `subscription: true|false|null` (есть ли наша подписка у MAX по последней проверке) — на `ok` не влияет.

## 5. Машина состояний сделки

### 5.1. Статусы
| Статус | Смысл | Терминальный | Эмодзи в карточке |
|---|---|---|---|
| `awaiting_confirmation` | карточка создана, клиент ещё не подтвердил текущую версию | нет | ⏳ |
| `changes_requested` | клиент предложил изменения; ждём новую версию от исполнителя | нет | ✏️ |
| `declined` | клиент отказался | да | ⛔ |
| `expired` | клиент не подтвердил за 72 ч | да | ⌛ |
| `awaiting_prepayment` | условия подтверждены, ждём предоплату (> 0) | нет | 💳 |
| `scheduled` | всё согласовано (и предоплата получена, если была); ждём выполнения | нет | 📅 |
| `awaiting_acceptance` | исполнитель отметил «Выполнено», ждём приёмку клиентом | нет | 🔍 |
| `remarks` | клиент оставил замечания; ждём исполнителя | нет | ⚠️ |
| `awaiting_payment` | принято, ждём остаток (> 0) | нет | 💳 |
| `paid` | оплачено полностью; ждём чек от исполнителя (для `npd`/`ip_kkt`) | нет | 🧾 |
| `closed` | сделка закрыта, документы отправлены | да | ✅ |
| `cancelled` | отменена исполнителем, клиентом или системой после подтверждения | да | 🚫 |

Вычисляемые величины: `remaining = total − prepayment`; `paidTotal = Σ succeeded payments`.

### 5.2. Переходы
Формат: **из → триггер [кто] → условие → в**; далее — побочные эффекты (события §5.4, напоминания §10, уведомления §6.5).

| # | Из | Триггер | Кто | Условие | В | Эффекты |
|---|---|---|---|---|---|---|
| T1 | — | `POST /api/deals` | seller | валидная версия v1 | `awaiting_confirmation` | `expires_at = now + 72h`; событие `deal.created`; карточка исполнителю; напоминания `client_not_opened`(+24h), `confirmation_expired`(+72h) |
| T2 | `awaiting_confirmation` | клиент открыл ссылку (`bot_started` с `d_<id>`) | client | клиента ещё нет или это тот же клиент | без смены статуса | `client_user_id`, `client_joined_at`; событие `client.joined`; карточка клиенту; исполнителю уведомление N1; отмена `client_not_opened` |
| T3 | `awaiting_confirmation` | кнопка «Подтверждаю» (`cf:<id>:<v>`) | client | версия = текущая: сверяется под `FOR UPDATE`; не совпала — перехода нет, ответ карточкой с заметкой «Условия изменились — посмотрите новую версию»; кнопка без версии (карточки до ЗАДАЧА_04) проходит, только если текущая версия 1 | `awaiting_prepayment` если `prepayment > 0`, иначе `scheduled` | `confirmed_at` в версии и сделке; событие `version.confirmed`; напоминания: `prepayment_due`(+24h), `prepayment_overdue`(+48h) **или** `event_tomorrow`/`event_passed` (§10); карточки обеих сторон; исполнителю N2 |
| T4 | `awaiting_confirmation` | «Предложить изменения» + текст | client | текст 1–500 симв. | `changes_requested` | событие `version.change_requested {text}`; исполнителю N3 с текстом и кнопками «Изменить условия» (open_app) / «Оставить как есть» |
| T5 | `awaiting_confirmation`, `changes_requested` | «Изменить условия» (open_app `edit_<id>`) → `PUT /api/deals/:id` | seller | изменилось хотя бы одно поле условий (иначе 409 `no_changes`); из других статусов — 409 `deal_not_editable` | `awaiting_confirmation` | новая строка `deal_versions` (прежние не редактируются), `current_version + 1`, `status_changed_at = now` (напоминания перепланируются от новой версии), `expires_at = now + 72h`, `confirmed_at = NULL`; событие `version.created {version, changed[]}`; карточки обеих сторон (строка «Версия N, условия изменены …»); клиенту N4 с перечнем изменившихся полей; исполнителю «Условия #{id} обновлены, клиент получил версию N» |
| T6 | `changes_requested` | «Оставить как есть» | seller | — | `awaiting_confirmation` | `expires_at` обновить; клиенту N5 (та же версия) |
| T7 | `awaiting_confirmation` | «Отказаться» → «Отказаться от сделки» | client | — | `declined` | событие `deal.declined`; исполнителю N6; все напоминания → cancelled |
| T8 | `awaiting_confirmation`, `changes_requested` | таймер 72 ч | system | — | `expired` | событие `deal.expired`; обеим N7 (клиенту — только если открывал) |
| T9 | `awaiting_prepayment` | предоплата `succeeded` (вебхук / опрос / «Получил(а)») | system | платёж kind=prepayment | `scheduled` | `paid_at` не трогаем; событие `payment.succeeded`; напоминания `event_tomorrow`(−24h), `event_passed`(+2h) при наличии даты; обеим карточки; N8 обеим |
| T10 | `scheduled` | «Выполнено» | seller | — | `awaiting_acceptance` | `done_at`; событие `deal.done`; клиенту N9; напоминание `acceptance_due`(+24h) |
| T11 | `awaiting_acceptance` | «Принимаю» | client | — | `awaiting_payment` если `remaining > 0`, иначе `paid` | `accepted_at`; событие `deal.accepted`; исполнителю N10; если `awaiting_payment` — напоминания `payment_due`(+24h), `payment_overdue`(+72h); если сразу `paid` — выполняются эффекты T14 (`paid_at`, N13/T15, напоминания о чеке) |
| T12 | `awaiting_acceptance` | «Есть замечания» + текст | client | 1–500 симв. | `remarks` | событие `deal.remarks {text}`; исполнителю N11 |
| T13 | `remarks` | «Исправлено» | seller | — | `awaiting_acceptance` | событие `deal.fixed`; клиенту N12; напоминание `acceptance_due` заново |
| T14 | `awaiting_payment` | остаток `succeeded` | system | kind=final | `paid` | `paid_at`; событие `payment.succeeded`; если `tax_mode = none` → сразу T15; иначе исполнителю N13, напоминания `receipt_due`(+24h), `receipt_deadline`(7-е число следующего месяца 10:00) |
| T15 | `paid` | чек приложен **или** «Закрыть без чека» (подтверждение) **или** `tax_mode=none` | seller/system | — | `closed` | `closed_at`; событие `receipt.attached` / `deal.closed_without_receipt`; PDF-квитанция обеим (§11); чек клиенту (если есть); N14 обеим; все напоминания → cancelled |
| T16 | любой нетерминальный, кроме `paid` (после полной оплаты — только закрытие) | «Отменить сделку» → «Отменить сделку» в подтверждении (+ причина опц.) | seller | — | `cancelled` | `cancelled_by_role='seller'`; событие `deal.cancelled`; `cancel_refund_expected` по §5.3; другой стороне N15; напоминания → cancelled; живые платежи `pending` → canceled (у провайдера не отменяем — ссылка просто истечёт), `succeeded` — не трогаем (возврат вне продукта, текст в карточке) |

Всё остальное — запрещённый переход: обработчик отвечает `answerOnCallback` с текущей карточкой и коротким
пояснением E1 «Это действие уже недоступно — карточка обновлена». Проверка перехода — одна функция
`canTransition(deal, action, role)` в `domain/deal/state-machine.ts`, покрытая тестами таблицей выше.

Конкурентность: все переходы выполняются в транзакции с `SELECT … FOR UPDATE` строки `deals`; повторное нажатие
кнопки (двойной тап, повторный вебхук) — идемпотентно: если статус уже целевой — ответ «уже сделано» без побочных эффектов.

### 5.3. Правило отмены и предоплата
`cancel_rule` ∈ `free_24h` | `free_48h` | `nonrefundable` | `full_refund`. Ожидание возврата предоплаты при отмене
**клиентом** (T17), если предоплата получена (`succeeded`):
- `free_24h`: возврат ожидается, если `scheduled_at − now ≥ 24h` (или даты нет); иначе — нет;
- `free_48h`: то же с 48 ч;
- `nonrefundable`: нет; `full_refund`: да.
При отмене **исполнителем** (T16) с полученной предоплатой возврат ожидается всегда. Результат — `cancel_refund_expected`
и текст в карточке: «Предоплата 500 ₽: ожидается возврат» / «Предоплата 500 ₽ не возвращается по правилу отмены».
Сам возврат денег продукт не выполняет **[модель]**.

**Возвраты (решение 22.09).** Продукт фиксирует **обязательство** возврата — по правилу отмены, которое обе стороны
приняли при подтверждении, — и **факт**: у клиента в карточке отменённой сделки кнопка [Возврат получил(а)], у
исполнителя [Вернул(а) предоплату]; нажатие пишет событие `refund.confirmed` (статус сделки остаётся `cancelled`, машина
состояний не меняется), строка попадает в карточку и в квитанцию PDF. Деньги исполнитель возвращает тем же путём,
каким получил: перевод — переводом, оплату по ссылке — возвратом в своём эквайринге. Через 48 ч без подтверждения
бот напоминает исполнителю. Возврат через API провайдера (`POST /refunds` от имени исполнителя) — следующий шаг,
когда рейл «ссылка» станет эквайрингом исполнителя (§9.1 «Кто получатель по ссылке»). Если клиент успел сообщить о
переводе («Я перевёл(а)»), а сделку отменили, — возврат тоже ожидается: обе стороны получают текст «Клиент сообщал о
переводе {сумма} {время} — проверьте поступление и верните при необходимости».

### 6.3. `/start d_<public_id>`: вход клиента
Источники события **оба**: `bot_started` с `payload = 'd_<id>'` (первый старт или после остановки бота) **и** `message_created`
с текстом `/start d_<id>`; обработчик один, `joinDeal(user, chatId, publicId)`, идемпотентный.
Порядок проверок и тексты:
1. Сделка не найдена → **E2** «Не нашёл такую сделку. Проверьте ссылку или попросите исполнителя прислать её ещё раз»
2. Пользователь = исполнитель этой сделки → его карточка (в демо и клиентская) **новым сообщением внизу чата**, старая
   становится указателем «↓ Карточка #{id} ниже, это актуальная версия»; так же открываются названия-ссылки в `/deals`
   (ЗАДАЧА_04 A2). Пока клиента нет, строка S4 «как позвать клиента».
3. У сделки уже другой клиент → **E3** «По этой ссылке уже подтверждает другой человек. Попросите исполнителя создать новую сделку»
4. Сделка демо (`demo=true`) и пользователь ≠ исполнитель → **E4** «Это демо-сделка исполнителя, к ней нельзя присоединиться»
5. Статус терминальный → карточка клиента без кнопок и строка «Сделка завершена».
6. Иначе T2: привязать клиента, отправить **C-card** (§6.4) и приветствие **S2** (одним сообщением над карточкой):
   «Исполнитель **{seller}** предлагает сделку. Проверьте условия и подтвердите или предложите изменения.»

900 ₽ истекла, нужна новая» / «Оплата 900 ₽ отменена: недостаточно средств» / «Предоплата 900 ₽ получена 12 окт, 14:07 по

пара только для двух коротких ответов на один вопрос; главное действие первым рядом, «Отменить сделку» последним.
Карточка исполнителя до входа клиента: [Отправить клиенту (link → `https://max.ru/:share?text={urlencoded «Подтвердите условия:
{название}, {дата}»\n{ссылка}}`), ссылка ровно один раз, CONTRACTS §5.3] [Скопировать ссылку (clipboard)]
[Изменить условия (open_app `edit_{id}`)] [🧪 Открыть как клиент (`dm:{id}`)] [Отменить сделку (`cn:{id}`)].
«Изменить условия» есть у исполнителя в `awaiting_confirmation` (и до, и после входа клиента) и в `changes_requested`.
Клиент: [Подтверждаю (`cf:{id}:{v}`, номер версии)] [Предложить изменения] [Отказаться]; оплата: [Оплатить по ссылке]
[Перевести по реквизитам]; живая ссылка: [Оплатить {sum} (link)] [Проверить оплату]; после неудачной ссылки [Новая ссылка];
приёмка: [Принимаю] + [Есть замечания] парой. Исполнитель: [Напомнить клиенту], [Выполнено], [Исправлено],
[Приложить чек] [Закрыть без чека]; закрытые: [Квитанция PDF] [Повторить сделку (open_app `repeat_{id}`, не у демо)];
отменённая с возвратом: [Вернул(а) предоплату] / у клиента [Возврат получил(а)].

**Ответ на нажатие всегда карточкой (правило, 22.09).** `POST /answers` в MAX **правит сообщение, на кнопке
которого нажали**. Поэтому любое нажатие кнопки на сообщении-карточке отвечается перерисованной карточкой
(`answerWithCard`): реакция на нажатие («уже сделано», E1–E13, запрос ввода, «Напоминание отправлено клиенту») встаёт
строкой-заметкой над текстом карточки, без эмодзи; на время подтверждения необратимого действия клавиатура карточки
заменяется на [Отменить сделку / Отказаться от сделки / Закрыть без чека] [Назад] (у исполнителя при отмене [Без причины]
[Оставить сделку]; «Назад» снимает ожидание причины). Остальные карточки сделки обновляются правкой (`syncCards` с
`skipMid` нажатой). Текстом без карточки бот отвечает только на кнопки вне карточки: уведомления, меню, список `/deals`.
«Открыть сделку» вне карточки (и повторный вход клиента по ссылке) присылает карточку новым сообщением вниз чата.

Рейл «перевод» рисует сама карточка:
- клиент, платёж `transfer/pending`: вместо строки оплаты блок «Переведите **{sum}** по реквизитам и нажмите
  «Я перевёл(а)»», реквизиты кодом, «🧪 Перевод продукт не видит, его подтверждают обе стороны кнопками»;
  кнопки [Я перевёл(а)] [Другой способ оплаты];
- клиент, `transfer/claimed`: «Вы сообщили о переводе {sum} {время}. Ждём подтверждения исполнителя», кнопок рейла нет;
- исполнитель, `transfer/pending`: «Предоплата {sum}: клиент выбрал перевод по реквизитам, ждём перевода»;
- исполнитель, `transfer/claimed`: «… клиент сообщил о переводе {время}. Проверьте поступление и подтвердите» и
  [Получил(а)] [Не вижу перевода] прямо в карточке (P2 остаётся уведомлением: правка карточки push-уведомления не даёт).

### 6.6. Ожидание ввода (`user_inputs`)
Бот запрашивает текст/файл после нажатия кнопки; ввод ждётся 30 минут:
| kind | Запрос | Валидация | Ошибка |
|---|---|---|---|
| `change_request` | «Напишите одним сообщением, что изменить. Например: «давайте 15:00 и без предоплаты»» | текст 1–500 | E5 «Слишком длинно: нужно до 500 символов. Сократите и пришлите ещё раз» |
| `remarks` | «Опишите замечания одним сообщением» | 1–500 | E5 |
| `receipt` | «Пришлите чек из «Мой налог» одним сообщением: фото или PDF» | вложение `image` или `file` (pdf/jpg/png), ≤ 20 МБ | E6 «Нужен файл или фото. Пришлите чек вложением» |
| `cancel_reason` | «Напишите причину отмены одним сообщением или нажмите «Без причины»» + кнопки [Без причины (`cn:y:{id}:none`)] [Оставить сделку (`op:{id}`)] | 0–300 | E5 |
Ответы: «Передали предложение исполнителю. Ждём новые условия», «Передали замечания исполнителю. Ждём исправлений»,
«Сделка #{id} отменена», «Чек принят. Готовлю квитанцию, пришлю отдельным сообщением».
Чек пересылается клиенту тем же `token` входящего вложения (`attachments[i].payload.token` для `image`/`file`); если `token`
отсутствует, скачать по `url` и загрузить через `uploadFile/uploadImage` заново. Тип и имя файла сохраняются в `receipts`.
Любое сообщение вне ожидания ввода → **S3** «Я понимаю только кнопки и команды. Откройте /deals или /new» (и меню S1).
Просроченный ввод → **E8** «Время ожидания истекло. Нажмите кнопку ещё раз»

### 7.1. Общее
React 19.2.8 + MAX UI 0.5.0, hash-роутинг (`/app/#/new`, `#/new?from=:id`, `#/deals`, `#/deals/:id`, `#/deals/:id/edit`, `#/deals/:id/time`,

активный пункт акцентом, на «Сделках» счётчик сделок, где нужен ход пользователя (у клиента подтвердить, внести предоплату,

листом снизу «Уйти без сохранения?». **Шапка** экрана: логотип 24 px (в тёмной теме белый) и заголовок.
Старт: `window.WebApp.initDataUnsafe.start_param`: `new` → `#/new`; `deals` → `#/deals`; `settings` → `#/settings`;
`d_<id>` → `#/done/<id>`; `edit_<id>` → `#/deals/<id>/edit` (кнопка «Изменить условия» в карточке исполнителя, §7.5);
`repeat_<id>` → `#/new?from=<id>` (кнопка «Повторить сделку» у завершённой сделки, §7.5); `deal_<id>` → `#/deals/<id>` (экран сделки, §7.9); `time_<id>` → `#/deals/<id>/time` (выбор времени клиентом, §7.10). `<id>` 10 символов `[A-Za-z0-9]`.
Авторизация: каждый запрос к `/api` с заголовком `X-Max-Init-Data: {window.WebApp.initData}` (§9.4).
Вне MAX (initData нет) экран **W0**: логотип 96 px, «Откройте мини-приложение внутри MAX», «Ссылка работает в приложении
MAX на телефоне или на web.max.ru», кнопка «Открыть в MAX»; при `NODE_ENV=development` и `DEV_FAKE_USER_ID` работа без Bridge.
initData есть, но сервер ответил 401: экран «Не удалось подтвердить вход через MAX» / «Закройте и откройте мини-приложение
ещё раз» + «Повторить».
Состояния каждого экрана: загрузка (скелет блоков), данные или пустое (иконка, заголовок, строка, до двух кнопок), ошибка
(заголовок с сутью, текст, «Повторить» и второй выход), успех действия (Snackbar на 5 секунд с одним действием и переход).
**История «назад» (ЗАДАЧА_08 A).** Свой стек экранов (`webapp/src/nav.ts`), адрес меняется `replaceState`. `BackButton` MAX
виден, пока в стеке больше одного экрана, и снимает верхний; на экране, с которого открыли мини-приложение (кнопкой в чате
или по `start_param`), кнопка скрыта, и «назад» закрывает приложение средствами MAX. Переход на экран, который уже есть в
стеке (вкладка туда-обратно), возвращает к нему и отрезает всё выше; после отправки формы «Готово» заменяет форму.

`HapticFeedback.notificationOccurred('success'|'error')` после создания и ошибки (если доступно).
Время везде по Москве: «(МСК)» у даты, «время МСК» один раз над расписанием и списком; в строках «сегодня, 14:00».

Кнопка «Создать сделку» (при повторе тому же клиенту «Создать и отправить клиенту»), под ней «Карточка появится в вашем

### 7.3. Экран «Готово» (`#/done/:id`)
Заголовок «Сделка создана», плашка «ждём подтверждения», превью карточки так, как её увидит клиент (текст как в чате, без
разметки и кнопок), строка «Ссылка для клиента» с кнопкой «Скопировать» (Snackbar «Ссылка скопирована»), кнопки «Отправить
клиенту» (`WebApp.shareMaxContent({ text, link })`, при отказе `openLink('https://max.ru/:share?text=…')`, при сбое Snackbar
«Не удалось открыть отправку. Скопируйте ссылку и пришлите её клиенту»), «Открыть чат с ботом», «К сделке» (экран сделки §7.9), «Все сделки».
Экран утверждает только то, что подтвердил ответ сервера:
- `card_sent: true`: внизу «Карточка уже в вашем чате с ботом, там вы увидите, когда клиент откроет ссылку»;
- `card_sent: false` (у исполнителя нет диалога с ботом): шаг «Откройте чат с ботом и нажмите «Начать»: карточка придёт
  туда» с кнопкой `openMaxLink('https://max.ru/{bot}?start=d_{id}')`;
- экран открыт без ответа создания (перезагрузка, прямая ссылка): заголовок «Сделка #id», условия подгружаются из
  `GET /api/deals/:id` (скелет, ошибка с «Повторить» и «Все сделки», чужая сделка «Это не ваша сделка»), о доставке ничего
  не утверждается;
- повтор с тем же клиентом, `client_card_sent: true`: заголовок «Карточка ушла клиенту», подпись «{имя} увидит её в чате с
  ботом. Ждём подтверждения»; блока ссылки и «Отправить клиенту» нет;
- `client_no_dialog: true`: обычный экран со ссылкой и строкой «{имя} ещё не начинал(а) диалог с ботом, поэтому отправьте
  ссылку сами».

### 7.4. Экран «Сделки» (`#/deals`)
Данные одним запросом `GET /api/deals?role=all&filter=all` (до 200 строк); вкладки, фильтры и дни считаются на клиенте.
**Вкладки** (сегмент-контрол): «Исполнитель» / «Клиент». Вторая видна, только если есть клиентская сделка; если
исполнительских нет, а клиентские есть, сразу открыта «Клиент». Демо-сделка только во вкладке исполнителя, с плашкой «демо».
**Вид** (сегмент-контрол): «Расписание» / «Список»; по умолчанию исполнителю расписание, клиенту список; выбор запоминается
на устройстве.
**Расписание**: лента дней сегодня минус 7 дней и плюс 21 день (день недели, число, под ним число сделок), заголовок дня
(«Сегодня, понедельник, 28 сентября», «3 сделки, время МСК») и строки `CellSimple`: над названием время «14:00», название,
под ним имя клиента (у исполнителя; клиенту имени исполнителя API списка не отдаёт), справа сумма и плашка статуса.
Пустой день «Сделок нет». Отменённые, отклонённые и истёкшие в расписание не попадают. Сделки без даты блоком «Без даты»;
позже трёх недель строка «Позже трёх недель: ещё N сделок» с «Открыть список».
**Список**: фильтры «Активные / К оплате / Закрытые / Все»; строка: название (плашка «демо»), под ним «12 окт, 14:00»,
справа сумма и плашка статуса; действующие ближайшие сверху, закрытые и «Все» свежие изменения сверху; под списком «Время МСК».
**Строка открывает экран сделки** `#/deals/:id` (§7.9, ЗАДАЧА_08 B), и в «Списке», и в «Расписании». Под строкой: «Открыть в чате» (всегда), исполнителю в
`awaiting_confirmation`/`changes_requested` «Изменить условия» (§7.5), у закрытых (кроме демо) «Повторить сделку» (§7.5).
Состояния: скелет из трёх строк; ошибка «Не удалось загрузить сделки» + «Повторить»; пустое по вкладке и фильтру
(исполнителю «Сделок пока нет» / «Создайте первую, это займёт полминуты» + «Новая сделка»; клиенту «Здесь появятся сделки,
которые вам предложат»).

### 7.5. Правка условий (`#/deals/:id/edit`, T5) и «Повторить сделку» (`#/new?from=:id`): только исполнитель
Правка: та же форма §7.2, предзаполненная из `GET /api/deals/:id`. Заголовок «Изменить условия», подпись «Сделка #id. Клиент
получит новую версию и подтвердит её заново», блоков «Услуга» и «О вас» нет, кнопка «Отправить новые условия». Отправка
`PUT /api/deals/:id` (тело как у `POST`, без `profile`).
- `can_edit: false`: экран-объяснение без формы (клиент уже подтвердил: «Клиент уже подтвердил прежние условия. Чтобы
  поменять их, отмените сделку и создайте новую»; завершена: «Условия завершённой сделки не меняются»; открыл клиент:
  «…нажмите «Предложить изменения» на карточке сделки в чате»; 403: «Менять условия может только исполнитель этой сделки»),
  кнопки «Все сделки» и «Открыть в чате».
- Успех: экран «Условия отправлены» («Карточка обновилась у вас и у клиента. Клиент подтвердит версию N заново.»; при
  `client_notified: false` «…Клиенту сообщение не дошло: напомните ему открыть карточку по ссылке.») + «Все сделки» / «Открыть чат».
- 403 или 409 `deal_not_editable`: тот же экран «клиент уже подтвердил».
- 409 `no_changes` (и та же проверка на клиенте до запроса): Snackbar «Вы ничего не изменили», остаёмся на форме.
- Сеть, таймаут, 5xx, 404/405: Snackbar с текстом и «Повторить»; ввод не теряется.
- Загрузка: скелет формы; ошибка загрузки «Не удалось загрузить сделку» + «Повторить» и «Все сделки».

**Повторить сделку** (`#/new?from=:id`, `start_param` `repeat_<id>`). Та же форма, предзаполненная всем, **кроме даты**
(была дата: «Когда» пустое и в фокусе; не было: «Без даты»). Заголовок «Повторить сделку», подпись «Условия из сделки #id,
дата новая». Если `same_client_available`, блок «Клиент» с переключателем «Тот же клиент: {имя}» (по умолчанию включён;
кнопка «Создать и отправить клиенту»). Отправка `POST /api/deals` с `repeat_of` и `same_client`; дальше «Готово» (§7.3).
`can_repeat: false` или 403: экран «Повторить нельзя» с причиной (демо, ещё идёт, не исполнитель) + «Новая сделка» / «Все сделки».

### 7.6a. «Мои услуги» исполнителя (`#/settings/services`) — ЗАДАЧА_08 C
Услуга — сохранённые условия, из которых исполнитель быстро собирает карточку: название (2–80), уточнения (≤ 1000), цена
(1 … 1 000 000 ₽), длительность (15 … 720 мин, шаг 15, по умолчанию 60 — нужна части D: занятость), предоплата
(нет / процент 1–100 / сумма ≤ цены), правило отмены, порядок, «показывать» (скрытая в форме не предлагается). Это **не
витрина**: клиент список услуг не видит нигде, услуга только заполняет форму исполнителя. До 50 услуг у исполнителя.
- Экран «Мои услуги» (из «Настроек»): список по порядку, стрелки «выше / ниже», «Добавить услугу»; скрытые — отдельным
  блоком «Скрытые». Пусто — «Сохраните то, что делаете чаще всего: карточка соберётся в одно нажатие» и чипы-примеры
  ниш (§7.6): пример открывает форму услуги с его названием, предоплатой и правилом (цену вводит исполнитель).
- Форма услуги (`#/settings/services/new`, `#/settings/services/:id`): поля выше, «Сохранить», у существующей —
  «Скрыть» / «Показывать снова». Удаления нет: на услугу ссылаются сделки.
- «Новая сделка» (§7.2): если у исполнителя есть показываемые услуги, над полями блок «Выбрать услугу» (чипы: название
  и цена). Выбор подставляет всё, кроме даты: название, уточнения, сумму, предоплату (процент — сегментом, сумма —
  «Своя»), правило отмены; поля остаются редактируемыми; сделка запоминает услугу (`service_id`) и её длительность.
  Повторное нажатие выбранного чипа снимает выбор. Шаблоны ниш остаются ниже («Или начните с примера»); у заполненной
  формы без выбранной услуги — ссылка-кнопка «Сохранить как услугу» (`POST /api/services` из полей формы).
- «Повторить» (§7.5) берёт услугу прежней сделки (`service_id` из `GET /api/deals/:id`), даже если её потом скрыли.
  Правка условий (T5) показывает тот же блок; смена услуги меняет `service_id` и длительность сделки.

### 7.9. Экран сделки (`#/deals/:id`, `start_param` `deal_<id>`) — ЗАДАЧА_08 B
Открывается из строк «Списка» и «Расписания» (§7.4), кнопкой «К сделке» на «Готово» (§7.3), по `start_param` `deal_<id>`.
Данные — `GET /api/deals/:id/full`. Состояния: загрузка («Загружаем…»), ошибка с «Повторить» и «Все сделки», нет доступа

прочитал условия и действуешь, без прокрутки хронологии; найдено прогоном удобства 29.09):
1. Заголовок «{название}», подпись «#{id}» (+ бейдж «демо»), статус словом для роли (`status_text`).

3. Действия (п. 8 ниже) и подсказки «Оплата — в чате с ботом» / «Клиент сообщил о переводе — подтвердите в чате»

3a. Стороны: исполнитель, клиент («ещё не открыл ссылку», если нет).
4. Деньги: оплачено / остаток, платежи (вид, рейл, статус, время; ссылка ЮKassa помечена «тест», перевод — «подтверждают стороны»).

6. История версий (если версий > 1): версия · когда · сумма · предоплата · подтверждена ли клиентом · текст запроса изменений.
7. Документы: «Квитанция PDF» (в терминальном статусе — отправляется в чат с ботом, действие `receipt_pdf`: скачать файл
   с заголовком авторизации WebView не умеет), строка чека («Чек приложен {дата}», «Чек: до {дата}», «Чек не требуется»).

### 7.10. Другое время: выбор клиентом и занятость исполнителя (`#/deals/:id/time`, `start_param` `time_<id>`) — ЗАДАЧА_08 D
Клиент на «✏️ Предложить изменения» (карточка, §6.4) получает на месте карточки выбор: [🗓 Другое время (open_app
`time_<id>`)] [✍️ Написать текстом (`cr:t:<id>`)] [↩️ Назад (`op`)]. «Написать текстом» — прежний ввод §6.6 (T4).
На экране сделки (§7.9) «Предложить изменения» открывает тот же выбор листом.
**Экран выбора времени.** Данные — `GET /api/deals/:id/busy`. Лента из 30 дней (с сегодняшнего по МСК), под ней слоты
с шагом 30 минут с 08:00 до 21:30 (МСК); слот недоступен, если он раньше чем через 30 минут или визит длительностью
сделки (`duration_min`, по умолчанию 60) пересекается с занятым интервалом исполнителя; занятые подписаны «занято».
Текущее время сделки отмечено «сейчас». Выбор → «Предложить {дата время}» → `POST /api/deals/:id/time-proposals`.
Успех — экран «Предложение отправлено: исполнитель примет его одним нажатием, а вы подтвердите новую версию условий в
чате» + «Открыть чат». Ошибки: 409 `slot_busy` («Это время уже заняли. Выберите другое») — слоты перезагружаются;
409 `invalid_transition` — «Условия уже подтверждены или сделка завершена» + «Открыть чат». Три состояния экрана.
**Занятость** исполнителя — его сделки в `scheduled`, `awaiting_prepayment`, `awaiting_acceptance` с датой, интервал
`[scheduled_at, scheduled_at + duration_min)` (`NULL` — 60 минут), плюс **удержания**: принятые предложения времени,
версия с которыми ждёт подтверждения клиента (иначе два клиента, предложившие одно время, оба получили бы его).
Текущая сделка в занятость не входит. Интервалы отдаются слитыми, без названий и клиентов (не раскрываем чужие записи).
**Предложение** — только клиент сделки (в демо — исполнитель с `as=client`), статус `awaiting_confirmation` или
`changes_requested`, время на сетке и свободно: из `awaiting_confirmation` это T4 (событие `version.change_requested
{text: «Предлагаю другое время: …», proposal_id}`), из `changes_requested` — без перехода; в обоих случаях событие
`time.proposed {proposal_id, scheduled_at}` и строка `time_proposals` (`pending`; прежнее ожидающее предложение этой
сделки — `superseded`). Исполнителю **N3T**: «🗓 {client} предлагает другое время по #{id}: {дата} (МСК).» + [✅ Принять
{дд.мм чч:мм}] (`tp:<id>:<proposal_id>`) [✏️ Предложить другое (open_app `edit_<id>`)]. Та же кнопка «Принять» — первой в
карточке исполнителя в `changes_requested`, пока предложение ждёт (§5.5), и на экране сделки (действие `accept_time`, §7.9).
«Оставить как есть» (T6) и любая новая версия (T5) снимают ожидающее предложение (`superseded`).
**Принятие** (`tp`, только исполнитель): под блокировкой исполнителя (строка `users` FOR UPDATE) проверяем, что
предложение ещё `pending`, версия сделки та же, что при предложении, и время по-прежнему свободно. Свободно — новая версия
условий с этим временем тем же T5 (автор — исполнитель, остальные условия прежние), предложение `accepted`, клиенту N4,
исполнителю N4a; клиент подтверждает версию как обычно. Занято — предложение `taken`, исполнителю «Это время уже занято
другой записью — предложение снято. Предложите клиенту другое» + [✏️ Изменить условия]; клиенту — «Исполнитель не может
в {время}: оно уже занято. Предложите другое» + [🗓 Другое время]. Предложение устарело (версия сменилась, сделка ушла
дальше, время уже ближе 30 минут) — «Это предложение уже неактуально». Рабочих часов и перерывов нет — следующий шаг (SCALING).

### 7.11. Надёжность исполнителя и оценка клиента — ЗАДАЧА_08 E
Не рейтинг и не витрина: показатели — из фактов сделок, публичного профиля нет, оценку клиента видит только исполнитель.
**Показатели** (`domain/reliability.ts`, по завершённым — `closed` / `cancelled` — не-демо сделкам исполнителя):
- «Сделок закрыто» — число `closed`.
- «Без споров, %» — среди дошедших до «Выполнено» (закрытые и отменённые после `done_at`) доля закрытых без «Не вижу
  перевода» (`payment.not_received`); отмена после «Выполнено» — спор.
- «Чек в срок, %» — среди закрытых, где чек был нужен (не закрытых сами режимом «без чека»), доля с чеком, приложенным
  до 9-го числа месяца после оплаты (23:59 МСК, ст. 14 422-ФЗ); «Закрыть без чека» — не в срок.
- «Отмены исполнителем, %» — среди подтверждённых клиентом (есть `confirmed_at`) доля отменённых исполнителем.
- «Оценка клиентов» — среднее до десятых и число оценок, если они есть.
Нет базы для доли — показатель не выводится («пока нет данных»), а не «0 %».
**Где видно.** Исполнителю — в «Настройках» (блок «Надёжность»: пять строк и переключатель «Показывать надёжность
клиентам», по умолчанию выключен, `seller_profiles.show_reliability`) и на экране сделки исполнителя (строка под
сторонами). Клиенту — одна строка в его карточке в чате и на экране сделки: «🛡 {N} сделок, {M} % без споров», только если
исполнитель включил переключатель **и** закрытых сделок не меньше 3. Оценки клиенту не показываются никогда.
**Оценка клиента.** После закрытия (T15) клиенту приходит одно сообщение **R1** «⭐ Оцените работу по #{id}: {название}.
От 1 до 5, где 5 — отлично. Оценку увидит только исполнитель.» + пять кнопок [1]…[5] (`rt:<id>:<n>`, в одном ряду). Нажатие — оценка
сохраняется (одна на сделку: повтор — «Оценка уже сохранена»), сообщение правится на «Спасибо! Ваша оценка: {n} из 5.
Можно добавить комментарий одним сообщением» + [Без комментария (`rt:n:<id>`)]; ввод `rating_comment` ждётся 30 минут
(§6.6, до 500 символов). Исполнителю — **R2** «⭐ {client} оценил(а) работу по #{id}: {n} из 5.» (+ комментарий
отдельным сообщением **R3**, когда придёт). Демо: R1 приходит (помечен 🧪), но демо-сделки в показатели не входят.
Экран сделки исполнителя показывает оценку и комментарий в блоке «Стороны»; клиенту — его собственную оценку.
**API.** `GET /api/me` → `reliability: Reliability | null` (только исполнителю с профилем); `PUT /api/me/profile`
принимает `show_reliability?: boolean`. `DealFull` → `reliability_line: string | null` (строка для клиента / исполнителя)
и `rating: { score, comment } | null` (исполнителю и автору оценки).

## 8. Модель данных
DDL — `server/migrations/0001_init.sql` (первичен). Ключевые правила:
- `deals.public_id` — 10 символов из алфавита `A-Za-z0-9` (`nanoid` с custom alphabet); генерация с повтором при коллизии.
- Версия условий никогда не редактируется — только добавляется новая (`deal_versions`), `deals.current_version` двигается.
- В `payments` не более одного живого платежа на `(deal_id, kind)` — частичный уникальный индекс.
- `deal_events.seq` — под блокировкой строки сделки.
- `card_messages` хранит `mid` карточки каждой стороны; при неудачном `PUT /messages` (например, сообщение удалено)
  отправляем новую карточку и обновляем `mid`.
- `users.dialog_chat_id` заполняется из `bot_started.chat_id` и `message.recipient.chat_id`; `reply` в SDK шлёт по `chat_id`,
  а уведомления второй стороне — `sendMessageToUser(user_id)` (CONTRACTS §1.7) — оба варианта допустимы, используем
  `sendMessageToUser` для «чужой» стороны и `ctx.reply` для отвечающей.
- Удаление данных не предусмотрено в MVP (Won't); `dialog_removed`/`bot_stopped` → помечаем `users.dialog_chat_id = NULL`
  (уведомления перестают уходить до следующего `/start`).
- `deal_ratings` (`0008_reliability_and_ratings.sql`, ЗАДАЧА_08 E): оценка клиента 1–5 и необязательный комментарий,
  одна на сделку (PRIMARY KEY `deal_id`); `seller_profiles.show_reliability` (по умолчанию `false`); вид ввода
  `rating_comment` в `user_inputs`.
- `time_proposals` (`0007_time_proposals.sql`, ЗАДАЧА_08 D): предложения времени; не больше одного `pending` на сделку
  (частичный уникальный индекс), `base_version` — версия на момент предложения, `accepted_version` — версия, созданная
  принятием (удержание времени, §7.10).
- `seller_services` (`0006_seller_services.sql`, ЗАДАЧА_08 C): услуги исполнителя (§7.6a). У сделки — `deals.service_id`
  (`ON DELETE SET NULL`) и `deals.duration_min` — длительность **на момент создания** (или правки T5 со сменой услуги):
  правка услуги потом не сдвигает занятость уже договорённых визитов. `NULL` — считать 60 минут (§7.10).

## 9. Интеграции

### 9.1. Рейлы оплаты — устройство и переключение

**Кто получатель по ссылке (решение 22.09).** Рейл «ссылка» в MVP формируется в **тестовом магазине команды**, чтобы
показать интеграцию целиком: создание платежа, вебхук, статусы, отказы, истечение. В продукте этот рейл —
**собственный** эквайринг исполнителя: для ИП — его магазин ЮKassa или Т-Бизнес по API (ключи подключаются в
настройках профиля, `seller_profiles.acquiring` — следующий этап), для самозанятого — СБП-ссылка банка-партнёра или
рейл «перевод». Платформа деньги не принимает, не держит и не распределяет — поэтому она не платёжный агент (103-ФЗ),
не эскроу и не выбивает чеки за исполнителя (54-ФЗ и 422-ФЗ остаются на нём). Продукт — не приём денег, а
зафиксированная договорённость, статус у обеих сторон и доказательная квитанция. В интерфейсе рейл помечен
«🧪 Тестовый магазин ЮKassa».

Доступность кнопок в карточке клиента:
- «Оплатить по ссылке» — если `PAYMENT_PROVIDER != none` **и** `seller.link_enabled` **и** сумма ≥ минимума провайдера
  (ЮKassa 1 ₽).
- «Перевести по реквизитам» — если `seller.transfer_enabled` **и** `payout_details` не пуст (иначе кнопка есть, но ответ E12).
Оба могут быть доступны одновременно; клиент выбирает при каждом платеже. Выбор фиксируется в `payments.rail`.
Смена рейла: пока платёж `pending` по ссылке, клиент может нажать «Перевести» — ссылочный платёж помечаем `canceled`
(локально; у провайдера истечёт сам) и создаём `transfer`. Обратно — так же. Один живой платёж на (сделка, вид).

**Рейл «ссылка» [тест]** — `domain/payment/rails.ts::createLinkPayment(deal, kind)`:
1. Создать запись `payments` (`pending`, `idempotence_key`), затем вызвать провайдера (§9.2/9.3).
2. Ответить клиенту обновлённой карточкой: строка «Ссылка на оплату {sum} действует до {время}» + кнопки
   [Оплатить {sum} (link → `confirmation_url`)] [Проверить оплату (`pc:{id}:{payment_id}`)].
3. Подтверждение приходит вебхуком (§9.6) **или** опросом планировщика (§10.3) **или** кнопкой «Проверить оплату»
   (синхронный `GET` статуса). Любой путь ведёт в одну функцию `applyProviderStatus(payment, providerStatus)` — идемпотентную.
4. В карточке и README обязательная пометка: «оплата через **тестовый** магазин ЮKassa — реальные деньги не списываются».

**Рейл «перевод» [модель]** — клиент нажимает «Перевести по реквизитам»:
1. Создаём `payments` (`rail=transfer`, `provider=manual`, `pending`).
2. Клиенту обновлённая карточка, в которой вместо строки оплаты блок реквизитов (§6.4): «Переведите **{sum}** по
   реквизитам и нажмите «Я перевёл(а)»», `{payout_details}`, «🧪 Перевод продукт не видит, его подтверждают обе
   стороны кнопками». Кнопки: [Я перевёл(а) (`tr:c:{id}:{pid}`)] [Другой способ оплаты (`tr:x:{id}:{pid}`)].
   Отдельного сообщения P1 нет: ответ на нажатие правит саму карточку, и отдельный текст был бы тут же затёрт.
3. «Я перевёл(а)» → `claimed`, `claimed_at`; исполнителю **P2**: «💸 {client} сообщил(а) о переводе {sum} по #{id}.» /
   «Проверьте поступление и подтвердите.» + [Получил(а) (`tr:g:{id}:{pid}`)] [Не вижу перевода (`tr:n:{id}:{pid}`)].
4. «Получил(а)» → `succeeded` → T9/T14. «Не вижу перевода» → `pending`, событие `payment.not_received`, клиенту **P3**:
   «⚠️ Исполнитель пока не видит перевод {sum} по #{id}.» / «Проверьте операцию и нажмите «Я перевёл(а)» ещё раз, не раньше
   чем через 10 минут, или выберите другой способ оплаты.»
5. Клиент может нажать «Я перевёл(а)» не чаще 1 раза в 10 минут, в том числе после «Не вижу» (иначе E13). Со второго «Не вижу» подряд
   клиенту уходит P3_DISPUTE: оплата по ссылке и «продукт не арбитр: спор решают стороны, хронология — в квитанции».
Никаких банковских данных продукт не запрашивает и не хранит, кроме текста реквизитов, который исполнитель сам показывает клиенту.

### 9.4. Валидация `initData` (мини-приложение) — `docs/CONTRACTS.md` §4.1

## 10. Планировщик напоминаний

### 10.1. Принцип
Напоминания **материализуются** при каждом переходе (`domain/reminder/plan.ts::planReminders(deal)`): `pending` этой
сделки, которых нет в наборе для нового статуса, → `cancelled` (`last_error='replanned'`), затем набор вставляется.
`dedupe_key = <deal_id>:<kind>:<role>:<status_changed_at ISO>` — уникальный индекс защищает от дублей при повторном
планировании; строка с тем же ключом, погашенная перепланированием, оживает (`pending`), любая другая не трогается.
Так переход без смены статуса (T2 — ключи те же) не теряет `confirmation_expired`. Тик планировщика (30 с) берёт `pending` с `due_at <= now`
(`FOR UPDATE SKIP LOCKED`, порциями по 50), отправляет, ставит `sent`/`failed` (3 попытки, потом `failed`). Отправка
пропускается (status `cancelled`, `last_error='state_changed'`), если статус сделки уже не тот, для которого создано напоминание.

### 10.3. Прочие задания планировщика
- `payments-poll` (каждый тик): платежи `rail=link`, `status=pending`, `created_at < now − 30 с`, `expires_at > now` → опрос статуса
  провайдера (не чаще 1 раза в 60 с на платёж, поле `updated_at`); истёкшие → `expired` + карточка «Ссылка истекла» с кнопкой «Новая ссылка».
- `expire` — обрабатывается через напоминание `confirmation_expired` (единый механизм).
- `daily_digest` (каждый тик, одним `INSERT … ON CONFLICT DO NOTHING`): исполнителям с включённой сводкой, у кого на сегодня
  (сутки МСК) есть записи в scheduled / awaiting_prepayment / awaiting_acceptance, и только если момент сводки ещё впереди, —
  строка на сегодня. Выборка начинается со сделок по статусу, поэтому тик дешёвый. Смена `digest_time` через
  `PUT /api/me/profile` (поле `digest_time: number | null`; нет поля — не менять) сразу переносит сегодняшнюю ждущую строку
  на новое время, а если сводку выключили или новое время уже прошло — гасит её (`digest_off` / `digest_passed`); погашенную
  настройками строку новое будущее время оживляет. Отправленную не трогает ничто — вторая сводка в тот же день не приходит.
- Защита: тик не стартует, пока предыдущий не завершён; ошибки задания логируются и не роняют процесс.

## 12. Демо-режим «Открыть как клиент»

Цель: эксперт проходит сценарий целиком с одного аккаунта. Реализация:
- Включается `DEMO_MODE=true`. Кнопка 🧪 «Открыть как клиент» есть в карточке исполнителя, пока `client_user_id IS NULL`.
- Нажатие → `deals.demo = true`, `client_user_id = seller_user_id`, событие `demo.opened`, затем стандартный T2: в **тот же чат**
  отправляется клиентская карточка с префиксной строкой «🧪 **Демо: так видит клиент**» и клиентскими кнопками.
  Все клиентские действия обрабатываются обычными обработчиками; `actor_role = 'client_demo'`.
- Уведомления «второй стороне» в демо тоже приходят в этот чат — с префиксом «🧪 (клиенту)» / «🧪 (исполнителю)», чтобы
  экспериментатор видел обе стороны. Две карточки (исполнителя и «клиента») живут в одном чате и обновляются каждая.
- Помечено: в карточках, в списке сделок (бейдж «демо»), в PDF (водяной знак), в README (раздел «Тестовые данные»).
- Реальный клиент не может присоединиться к демо-сделке (E4). Обратной операции («сделать реальной») нет — создать новую.
- Кнопка «Демо: пройти одному» (меню S1 → «🧪 Попробовать», или `/new`) создаёт сделку по шаблону `beauty`: «Маникюр с покрытием», завтра 14:00,
  2 500 ₽, предоплата 500 ₽, `free_24h`, и сразу открывает её как клиент.
- При `DEMO_MODE=false` кнопки скрыты, а обработчики отвечают E1.

## 13. Диплинки и payload

| Ссылка | Формат | Где приходит |
|---|---|---|
| Клиенту в сделку | `https://max.ru/{bot}?start=d_{public_id}` | `bot_started.payload = 'd_<id>'` (≤ 128 симв.) |
| Мини-приложение, экран | `https://max.ru/{bot}?startapp=new` \| `deals` \| `settings` \| `d_{public_id}` \| `edit_{public_id}` \| `repeat_{public_id}` \| `deal_{public_id}` \| `time_{public_id}` | `initDataUnsafe.start_param` (только `A-Za-z0-9_-`, ≤ 512); кнопки open_app бота передают то же в `payload`: `edit_<id>` — «✏️ Изменить условия» (T5), `repeat_<id>` — «🔁 Повторить» у завершённой сделки исполнителя (§5.5) |
| Шеринг | `https://max.ru/:share?text={urlencoded}` | экран «Отправить в MAX» |
Payload `d_<id>`: `^d_[A-Za-z0-9]{10}$`; всё иное в `?start=` — игнорируется (меню S1). Ссылка — секрет-возможность (unguessable id),
других прав доступа к ней нет; повторное открытие тем же клиентом — идемпотентно.
Callback payload кнопок: `^[a-z]{2}(:[a-z])?:[A-Za-z0-9]{10}(:[A-Za-z0-9]+)?$`, коды: `cf` подтвердить (`cf:<id>:<v>` — номер версии условий; без `:<v>` — только версия 1, §5.2 T3), `cr` предложить изменения, `dc` отказаться, `dc:y` подтвердить отказ,
`pl` оплата по ссылке, `pt` перевод, `tr:c|g|n|x` (перевёл / получил / не вижу / отмена рейла), `pc` проверить оплату, `pe` эмулировать (tbank demo), `nl` новая ссылка, `dn` выполнено, `ac` принять,
`rm` замечания, `fx` исправлено, `rc` приложить чек, `nc` закрыть без чека, `nc:y` подтвердить закрытие без чека, `cn` отменить, `cn:y` подтвердить отмену (`cn:y:<id>:none` — без причины), `ka` оставить как есть,
`rs` напомнить клиенту, `rt:<id>:<n>` оценка 1–5 и `rt:n:<id>` «Без комментария» (§7.11), `dm` демо, `op` открыть карточку, `pdf` квитанция, `rf:s|c` возврат (§5.3); кнопки меню без id сделки:
`help`, `try` (экран «Попробовать»), `menu` (назад в меню), `dm:new`, `ex:new`; «Другое время» (ЗАДАЧА_08 D): `cr` показывает выбор
[🗓 Другое время (open_app `time_<id>`)] [✍️ Написать текстом (`cr:t:<id>`)] [↩️ Назад], `tp:<id>:<proposal_id>` — принять
предложенное время. Кнопка с неизвестным payload → E1.

## 14. Обработка ошибок и краевые случаи (обязательные тесты)
1. Двойное нажатие «Подтверждаю» → второй ответ «уже подтверждено», без второго события.
2. Повторный вебхук `payment.succeeded` → `ignored:duplicate`, без второго перехода.
3. Вебхук с чужим `metadata.deal` → `ignored:foreign`.
4. `PUT /messages` вернул `success:false` (карточка удалена) → новая карточка, `mid` обновлён.
5. Клиент открыл ссылку дважды / с другого устройства → одна привязка.
6. Исполнитель открыл собственную ссылку → карточка исполнителя, не клиента.
7. Ссылка на оплату истекла → статус `expired`, кнопка «Новая ссылка» создаёт новый платёж с новым `Idempotence-Key`.
8. Провайдер недоступен (таймаут) → E9, платёж `canceled` локально, кнопка доступна снова.
9. Сообщение с вложением без ожидания ввода → S3.
10. Файл чека > 20 МБ или не image/pdf → E6.
11. `scheduled_at` в прошлом при создании → 400 `validation` с текстом поля.
12. Пользователь заблокировал бота (`bot_stopped`) → уведомления ему помечаются `no_chat`, сделка живёт.
13. Рестарт процесса во время ожидания ввода → состояние в `user_inputs`, ввод принимается.
14. Два экземпляра с одним токеном → документировано в README (запрещено); код не защищает.
15. Нагрузка: 20 сделок × 2 карточки обновляются за ≤ 10 с (троттлинг 2 msg/с на чат — чаты разные).

## 17. Нефункциональные требования
- Безопасность: секреты только в env; initData/HMAC проверки; `timingSafeEqual`; входные данные — zod; SQL — только параметризованные;
  никаких реквизитов карт; логи без PII (телефон маской); rate-limit `/api` 60 req/мин на пользователя, `/webhooks` — 600/мин на IP.
- Надёжность: внешние вызовы с таймаутом 10 с; идемпотентность (§5.2, §9.6, §10.1); транзакции на переходах; graceful shutdown.
- Производительность: карточка рендерится < 50 мс; PDF < 1 с; тик планировщика < 5 с при 1 000 напоминаний.
- Тесты (vitest): машина состояний (таблица §5.2 полностью), правило отмены §5.3, `initData` (пример из CONTRACTS), Т-Банк `Token`
  (пример из CONTRACTS §3.2 → ожидаемый hex), разбор статусов ЮKassa/Т-Банк, планирование напоминаний по датам (фиксированное «сейчас»).
- Совместимость: MAX iOS/Android/desktop/web; мини-приложение — ширина 360–430 px и desktop; без внешних CDN, кроме `st.max.ru` (Bridge).

## 19. Ответы на вопросы, которые возникнут у читателя впервые
- **Где взять ник бота?** `GET /me` при старте; до этого — `MAX_BOT_USERNAME` пуст, диплинки не строятся; при `MAX_MODE=off` ссылки показываются с `{bot}` = «bot».
- **Что, если у клиента нет диалога с ботом?** Ссылка `?start=` его создаёт — это единственный способ (бот не пишет первым).
- **Почему карточка — два сообщения, а не одно общее?** У бота нет общего чата сторон (создать чат он не может); у каждой стороны своё сообщение с одинаковым состоянием.
- **Почему статус обновляем и на месте, и отдельным сообщением?** Правка на месте не даёт push-уведомления; короткое сообщение — даёт.
- **Почему long polling локально и webhook на VPS?** Webhook требует HTTPS:443 с доверенным сертификатом; локально его нет. Один токен — один экземпляр (SDK стирает подписки).
- **Как эксперт проверит одним аккаунтом?** Демо-режим §12 плюс «🧪 Попробовать» → «Демо: пройти одному» в меню.
- **Что с деньгами?** Продукт их не касается (§9.1). Эквайринг — тестовые среды. Это сказано в README, в презентации и в карточке.
- **Что делать, если MAX UI не собирается с нашей версией React?** MAX UI требует ровно `react 19.2.8` — зафиксировано; при конфликте — свои компоненты на токенах из `docs/DESIGN.md`, запись в ДОПУЩЕНИЯ.
- **Сертификат Минцифры?** `certs/README.md`; без него `platform-api2.max.ru` не откроется из Node в Docker — это первая проверка в ЗАДАЧА_01.
- **Часовой пояс?** Всё показываем в Europe/Moscow; храним UTC; напоминания по МСК.
- **Как мини-приложение привязывается к боту на хакатоне?** URL `PUBLIC_BASE_URL/app/` отправляет Екатерина через форму организаторов
  (https://sbor-ssylok-dlya-mini-prilojeniy.testograf.ru/, из письма с токеном) после деплоя на VPS. Кабинета business.max.ru у команды нет,
  поэтому URL должен быть стабильным с первой подачи; до привязки сценарий проходится через демо-сделку из меню (§12) и команду `/new`.
- **Что делать исполнителю с «Предложить изменения»?** «Изменить условия» в уведомлении N3 открывает мини-приложение сразу на
  форме этой сделки (`edit_<id>`, §7.5) — клиент получает версию 2 с перечнем изменений (T5). «Оставить как есть» и «Отменить» работают
  всегда. Текстовое редактирование в боте — Won't.
- **Как узнать, какое событие приходит при повторном нажатии диплинка?** Проверить в шаге 0 ЗАДАЧА_01 с логированием `DEBUG=max:*`;
  обработчик принимает оба источника (§6.3).
- **Что считать «основным сценарием» для жюри?** Создать сделку → отправить/открыть как клиент → подтвердить → предоплата (перевод «перевёл/получил» или тестовая ссылка) → выполнено → принято → остаток → чек → квитанция PDF обеим сторонам. Порядок проверки — README §«Сценарий проверки».
