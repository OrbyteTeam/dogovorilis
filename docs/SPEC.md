## 1. Продукт в одном абзаце

**Договорились** — бот и мини-приложение в MAX, где самозанятый или микро-ИП фиксирует договорённость с клиентом
(что / когда / сколько / предоплата / правило отмены) одной карточкой, клиент подтверждает её кнопкой в чате,
предоплата и остаток проходят по выбранному рейлу (ссылка эквайринга или перевод), статус обновляется
у обеих сторон в одном и том же сообщении, бот сам напоминает о визите, оплате и чеке, а по завершении обе
стороны получают чек и квитанцию о сделке PDF. Мы не касаемся денег: платёж идёт напрямую исполнителю.

**Актуальность (для презентации и README):**
- 17,26 млн самозанятых, 227,5 млн чеков в месяц (ФНС, авг. 2026); самозанятым открыли бизнес-платформу MAX
  15.06.2026; 57 % МСБ ведут дела «в мессенджерах и заметках», CRM — у 27 % (МТС/Авито, дек. 2025).
- No-show по записи 18–20 % (YCLIENTS/ProDoctorov); предоплата снижает его на 40–60 %; 31 % МСБ с существенной
  просроченной дебиторкой (ПСБ/НАФИ, дек. 2025); ЮKassa отключила чеки самозанятым с 29.12.2025.
- Реальный кейс из MAX: «Есть скрины переписки в Максе, что работа выполнена и клиент её принял» — долг 131 650 ₽
  (ИП по ремонту оборудования, Правовед.ru, 2026). Скрин ≠ подтверждённая договорённость.
- **Смарт-контракты:** Банк России 18.06.2026 опубликовал концепцию «Платформы коммерческих смарт-контрактов
  в цифровых рублях» — «программы, которые автоматически выполняют условия сделки при наступлении заранее
  определённых событий»; предложения принимаются до 30.09.2026 (https://cbr.ru/press/event/?id=32630).
  Карточка «условия → подтверждение → событие (приёмка) → оплата» — это прообраз условного платежа для
  микробизнеса без блокчейна; когда ПКСК откроется рынку, наша сделка становится шаблоном смарт-контракта
  (см. `docs/SCALING.md` §7).
Источники со ссылками — `../research/user_pains.md`, `../research/invoicing_audit.md`, `../research/context_max_payments.md`.

## 2. Пользователи, проблема, истории

**Сегмент пилота:** самозанятые и микро-ИП сферы услуг, договаривающиеся с клиентом в переписке: мастера красоты
на дому, репетиторы, ремонт техники/квартир, фотографы, кондитеры и флористы на заказ, фриланс. Клиент — физлицо
(иногда ИП). Обе стороны уже в MAX.

**Проблема:** Самозанятый мастер, когда договорённость с клиентом сложилась в переписке MAX, хочет получить
предоплату/оплату вовремя, не потерять слот и закрыть сделку чеком без штрафа, но условия размазаны по чату,
предоплату неловко просить и негде связать с записью, статус оплаты видит только он, а чек — ручное действие
в другом приложении с дедлайном «до 9-го», из-за чего no-show, споры «вы обещали другую цену / оплатил — не
оплатил», штраф 20 %/100 % за чек и потерянный доход.

**User stories, которые обязан закрывать MVP** (дословные цитаты — `../research/user_pains.md`, коды A1…E3):
1. (A1, A2) Мастер маникюра: запись подтверждается предоплатой с понятным правилом отмены, просить не приходится —
   правило живёт в карточке.
2. (A3) ИП по ремонту: изменение цены по ходу работ фиксируется новой версией карточки с подтверждением клиента.
3. (A4–A6) Репетитор: правило отмены и статус оплаты видны обеим сторонам; напоминает бот, а не человек.
4. (B3) Самозанятая: напоминание сформировать чек именно по этому поступлению до 9-го числа.
5. (A10, B12) Клиент: видит, на что договорились, статус и получает чек и квитанцию в тот же чат.
6. (E1, E2) Кондитер: макет/фото, вес, дата и сумма подтверждены одной кнопкой; выдача зафиксирована.

**Гипотеза и метрики:** если мастер фиксирует договорённость и предоплату одной карточкой с подтверждением
клиента, то доля сорванных записей снижается, время «договорились → оплачено» сокращается, доля оплат с чеком
в срок растёт. Метрики пилота: доля сделок с подтверждением; доля с предоплатой; no-show до/после; медиана часов
«создана → предоплата»; доля оплат с чеком до 9-го; число споров, разрешённых по карточке.

## 3. Роли и глоссарий

| Термин | Значение |
|---|---|
| Исполнитель (seller) | пользователь MAX, создавший сделку. Любой пользователь может быть исполнителем; отдельной регистрации нет |
| Клиент (client) | пользователь MAX, открывший ссылку сделки. В одной сделке ровно один клиент |
| Сделка (deal) | объект с версиями условий, платежами, событиями и статусом (§5) |
| Версия (version) | снимок условий: название, описание, дата, сумма, предоплата, правило отмены, фото. Подтверждается клиентом целиком |
| Карточка (card) | сообщение бота с текущим состоянием сделки и кнопками, своё у каждой стороны; обновляется на месте |
| Рейл (rail) | способ оплаты: `link` — ссылка эквайринга (провайдер ЮKassa **[тест]** или Т-Банк СБП **[тест]**); `transfer` — перевод по реквизитам исполнителя с ручным подтверждением обеих сторон **[модель]** |
| Квитанция (receipt PDF) | документ о сделке, который бот формирует сам (§11). Не фискальный чек |
| Чек | фискальный документ, который исполнитель формирует вне продукта («Мой налог» или касса) и прикладывает к сделке |
| Демо-режим | «Открыть как клиент»: исполнитель проходит клиентскую сторону в своём же чате (§12) |

## 4. Архитектура

### 4.1. Компоненты
```
┌─────────────── MAX ───────────────┐        ┌──────────── наш сервер (Docker: app) ────────────┐
│ чат исполнителя ↔ бот             │◄──────►│ transport/bot     — обработчики Bot API (SDK)     │
│ чат клиента     ↔ бот             │ Bot API│ transport/http    — Fastify: /api, /webhooks, /app │
│ мини-приложение (WebView, React)  │◄──────►│ domain/           — сделки, машина состояний,     │
└───────────────────────────────────┘  /api  │                     карточки, напоминания, PDF   │
                                             │ integrations/     — max, yookassa, tbank          │
   ЮKassa / Т-Банк ── webhooks ─────────────►│ db/               — pg, миграции, репозитории     │
                                             │ scheduler/        — тик 30 с: напоминания, опрос  │
                                             └──────────────┬────────────────────────────────────┘

```
Один процесс Node.js (бот + HTTP + планировщик) и одна БД. Второго процесса нет намеренно: проще запуск одной
командой, меньше точек отказа. Горизонтальное масштабирование — не цель MVP (см. SCALING §6).

### 4.4. Последовательность старта
1. `config.ts` валидирует env; при ошибке — понятное сообщение и `exit(1)`.
2. Подключение к БД с ретраем (10 попыток × 3 с) — compose ждёт `db` healthy, но ретрай всё равно нужен.
3. Миграции (`server/migrations/*.sql` по алфавиту, таблица `schema_migrations`, каждая в транзакции).
4. HTTP-сервер (Fastify) слушает `PORT`: `/healthz`, `/readyz`, `/api/*`, `/webhooks/*`, `/pay/return`, `/app/*`.
5. Бот (если `MAX_MODE != off`): `botInfo = await api.getMyInfo()` → `MAX_BOT_USERNAME` (env или `botInfo.username`);
   `setMyCommands` (§6.1); затем:
   - `polling`: `bot.start({ mode: 'polling', options: { allowedUpdates: [...] } })` — **внимание: SDK удаляет все
     webhook-подписки этого токена** (CONTRACTS §1.3). Поэтому один токен = один работающий экземпляр.
   - `webhook`: `bot.createWebhook({ domain: PUBLIC_BASE_URL host, path: '/webhooks/max', secret })` и
     регистрация возвращённого обработчика в Fastify как raw-handler (`POST /webhooks/max`). Порт наружу — 443
     через Caddy. Не использовать `startWebhook` (он поднимает второй http-сервер).
   - Ошибка `fetch failed` с `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`/`SELF_SIGNED_CERT_IN_CHAIN` → лог с подсказкой
     про `certs/russian_trusted_bundle.pem` и `exit(1)`.
   - `allowedUpdates`: `bot_started`, `message_created`, `message_callback`, `bot_stopped`, `dialog_cleared`.
6. Планировщик: `setInterval` 30 с; задания §10 и §9.6; защита от наложения (флаг «выполняется»).
7. Graceful shutdown: SIGTERM → stop polling/webhook, дождаться текущих обработчиков (≤ 10 с), закрыть pool.

### 4.5. Логи и наблюдаемость
pino JSON; каждый входящий update/запрос — `request_id`; в логах никогда нет токена, `initData`, реквизитов,
секретов провайдеров (маскировать). Ошибки интеграций — уровень `warn` с `provider`, `op`, `status`, `code`.
`/healthz` — процесс жив; `/readyz` — БД отвечает и (если `MAX_MODE != off`) бот инициализирован.

## 5. Машина состояний сделки

### 5.1. Статусы
| Статус | Смысл | Терминальный | Эмодзи в карточке |
|---|---|---|---|
| `awaiting_confirmation` | карточка создана, клиент ещё не подтвердил текущую версию | нет | ⏳ |
| `changes_requested` | клиент предложил изменения; ждём новую версию от исполнителя | нет | ✏️ |
| `declined` | клиент отказался | да | ⛔ |
| `expired` | клиент не подтвердил за 72 ч | да | ⌛ |
| `awaiting_prepayment` | условия подтверждены, ждём предоплату (> 0) | нет | 💳 |
| `scheduled` | всё согласовано (и предоплата получена, если была); ждём выполнения | нет | 📅 |
| `awaiting_acceptance` | исполнитель отметил «Выполнено», ждём приёмку клиентом | нет | 🔍 |
| `remarks` | клиент оставил замечания; ждём исполнителя | нет | ⚠️ |
| `awaiting_payment` | принято, ждём остаток (> 0) | нет | 💳 |
| `paid` | оплачено полностью; ждём чек от исполнителя (для `npd`/`ip_kkt`) | нет | 🧾 |
| `closed` | сделка закрыта, документы отправлены | да | ✅ |
| `cancelled` | отменена исполнителем, клиентом или системой после подтверждения | да | 🚫 |

Вычисляемые величины: `remaining = total − prepayment`; `paidTotal = Σ succeeded payments`.

### 5.2. Переходы
Формат: **из → триггер [кто] → условие → в**; далее — побочные эффекты (события §5.4, напоминания §10, уведомления §6.5).

| # | Из | Триггер | Кто | Условие | В | Эффекты |
|---|---|---|---|---|---|---|
| T1 | — | `POST /api/deals` | seller | валидная версия v1 | `awaiting_confirmation` | `expires_at = now + 72h`; событие `deal.created`; карточка исполнителю; напоминания `client_not_opened`(+24h), `confirmation_expired`(+72h) |
| T2 | `awaiting_confirmation` | клиент открыл ссылку (`bot_started` с `d_<id>`) | client | клиента ещё нет или это тот же клиент | без смены статуса | `client_user_id`, `client_joined_at`; событие `client.joined`; карточка клиенту; исполнителю уведомление N1; отмена `client_not_opened` |
| T3 | `awaiting_confirmation` | кнопка «Подтверждаю» | client | версия = текущая | `awaiting_prepayment` если `prepayment > 0`, иначе `scheduled` | `confirmed_at` в версии и сделке; событие `version.confirmed`; напоминания: `prepayment_due`(+24h), `prepayment_overdue`(+48h) **или** `event_tomorrow`/`event_passed` (§10); карточки обеих сторон; исполнителю N2 |
| T4 | `awaiting_confirmation` | «Предложить изменения» + текст | client | текст 1–500 симв. | `changes_requested` | событие `version.change_requested {text}`; исполнителю N3 с текстом и кнопками «Изменить условия» (open_app) / «Оставить как есть» |
| T5 | `changes_requested` | `PUT /api/deals/:id` (новая версия) | seller | — | `awaiting_confirmation` | `current_version + 1`, `expires_at = now + 72h`; событие `version.created {version}`; карточки обеих сторон; клиенту N4 |
| T6 | `changes_requested` | «Оставить как есть» | seller | — | `awaiting_confirmation` | `expires_at` обновить; клиенту N5 (та же версия) |
| T7 | `awaiting_confirmation` | «Отказаться» → «Да, отказаться» | client | — | `declined` | событие `deal.declined`; исполнителю N6; все напоминания → cancelled |
| T8 | `awaiting_confirmation`, `changes_requested` | таймер 72 ч | system | — | `expired` | событие `deal.expired`; обеим N7 (клиенту — только если открывал) |
| T9 | `awaiting_prepayment` | предоплата `succeeded` (вебхук / опрос / «Получил(а)») | system | платёж kind=prepayment | `scheduled` | `paid_at` не трогаем; событие `payment.succeeded`; напоминания `event_tomorrow`(−24h), `event_passed`(+2h) при наличии даты; обеим карточки; N8 обеим |
| T10 | `scheduled` | «Выполнено» | seller | — | `awaiting_acceptance` | `done_at`; событие `deal.done`; клиенту N9; напоминание `acceptance_due`(+24h) |
| T11 | `awaiting_acceptance` | «Принимаю» | client | — | `awaiting_payment` если `remaining > 0`, иначе `paid` | `accepted_at`; событие `deal.accepted`; исполнителю N10; если `awaiting_payment` — напоминания `payment_due`(+24h), `payment_overdue`(+72h); если сразу `paid` — выполняются эффекты T14 (`paid_at`, N13/T15, напоминания о чеке) |
| T12 | `awaiting_acceptance` | «Есть замечания» + текст | client | 1–500 симв. | `remarks` | событие `deal.remarks {text}`; исполнителю N11 |
| T13 | `remarks` | «Исправлено, проверьте» | seller | — | `awaiting_acceptance` | событие `deal.fixed`; клиенту N12; напоминание `acceptance_due` заново |
| T14 | `awaiting_payment` | остаток `succeeded` | system | kind=final | `paid` | `paid_at`; событие `payment.succeeded`; если `tax_mode = none` → сразу T15; иначе исполнителю N13, напоминания `receipt_due`(+24h), `receipt_deadline`(7-е число следующего месяца 10:00) |
| T15 | `paid` | чек приложен **или** «Закрыть без чека» (подтверждение) **или** `tax_mode=none` | seller/system | — | `closed` | `closed_at`; событие `receipt.attached` / `deal.closed_without_receipt`; PDF-квитанция обеим (§11); чек клиенту (если есть); N14 обеим; все напоминания → cancelled |
| T16 | любой нетерминальный, кроме `paid` (после полной оплаты — только закрытие) | «Отменить сделку» → «Да, отменить» (+ причина опц.) | seller | — | `cancelled` | `cancelled_by_role='seller'`; событие `deal.cancelled`; `cancel_refund_expected` по §5.3; другой стороне N15; напоминания → cancelled; живые платежи `pending` → canceled (у провайдера не отменяем — ссылка просто истечёт), `succeeded` — не трогаем (возврат вне продукта, текст в карточке) |
| T17 | `awaiting_prepayment`, `scheduled` | «Отменить» → «Да, отменить» | client | — | `cancelled` | `cancelled_by_role='client'`; `cancel_refund_expected` по §5.3; исполнителю N15 |
| T18 | `awaiting_acceptance`, `remarks`, `awaiting_payment` | «Отменить сделку» | client | — | **запрещено** | текст E7 «После выполнения работы отмена только по согласованию с исполнителем» |

Всё остальное — запрещённый переход: обработчик отвечает `answerOnCallback` с текущей карточкой и коротким
пояснением E1 «Это действие уже недоступно — карточка обновлена». Проверка перехода — одна функция
`canTransition(deal, action, role)` в `domain/deal/state-machine.ts`, покрытая тестами таблицей выше.

Конкурентность: все переходы выполняются в транзакции с `SELECT … FOR UPDATE` строки `deals`; повторное нажатие
кнопки (двойной тап, повторный вебхук) — идемпотентно: если статус уже целевой — ответ «уже сделано» без побочных эффектов.

### 5.3. Правило отмены и предоплата
`cancel_rule` ∈ `free_24h` | `free_48h` | `nonrefundable` | `full_refund`. Ожидание возврата предоплаты при отмене
**клиентом** (T17), если предоплата получена (`succeeded`):
- `free_24h`: возврат ожидается, если `scheduled_at − now ≥ 24h` (или даты нет); иначе — нет;
- `free_48h`: то же с 48 ч;
- `nonrefundable`: нет; `full_refund`: да.
При отмене **исполнителем** (T16) с полученной предоплатой возврат ожидается всегда. Результат — `cancel_refund_expected`
и текст в карточке: «Предоплата 500 ₽: ожидается возврат» / «Предоплата 500 ₽ не возвращается по правилу отмены».
Сам возврат денег продукт не выполняет **[модель]**.

**Возвраты (решение 22.09).** Продукт фиксирует **обязательство** возврата — по правилу отмены, которое обе стороны
приняли при подтверждении, — и **факт**: у клиента в карточке отменённой сделки кнопка [✅ Возврат получил(а)], у
исполнителя — [✅ Вернул(а)]; нажатие пишет событие `refund.confirmed` (статус сделки остаётся `cancelled`, машина
состояний не меняется), строка попадает в карточку и в квитанцию PDF. Деньги исполнитель возвращает тем же путём,
каким получил: перевод — переводом, оплату по ссылке — возвратом в своём эквайринге. Через 48 ч без подтверждения
бот напоминает исполнителю. Возврат через API провайдера (`POST /refunds` от имени исполнителя) — следующий шаг,
когда рейл «ссылка» станет эквайрингом исполнителя (§9.1 «Кто получатель по ссылке»). Если клиент успел сообщить о
переводе («Я перевёл(а)»), а сделку отменили, — возврат тоже ожидается: обе стороны получают текст «Клиент сообщал о
переводе {сумма} {время} — проверьте поступление и верните при необходимости».

### 6.2. `/start` без payload (и `bot_started` без payload)
Сохранить/обновить пользователя и `dialog_chat_id`. Текст **S1**:
```
👋 Это «Договорились» — карточка договорённости прямо в чате MAX.

Вы описываете, что, когда и за сколько; клиент подтверждает одной кнопкой; предоплата, статус, напоминания, чек и квитанция — здесь же, у обеих сторон.

Что дальше?
```
Кнопки (inline, 2 ряда): [➕ Новая сделка (open_app, payload `new`)] [📂 Мои сделки (open_app, `deals`)]
[⚙️ Настройки (open_app, `settings`)] [❓ Как это работает (callback `help`)].
Если `DEMO_MODE`: третий ряд [🧪 Попробовать на демо-сделке (callback `demo:new`)] — создаёт демо-сделку по
шаблону `beauty` с данными-примером и сразу открывает её как клиент (§12).

### 6.3. `/start d_<public_id>` — вход клиента
Источники события — **оба**: `bot_started` с `payload = 'd_<id>'` (первый старт или после остановки бота) **и** `message_created`
с текстом `/start d_<id>` (документация не описывает, какое событие приходит уже существующему собеседнику при нажатии диплинка —
проверяется в шаге 0 ЗАДАЧА_01; обработчик один — `joinDeal(user, chatId, publicId)`, идемпотентный).
Порядок проверок и тексты:
1. Сделка не найдена → **E2** «Не нашёл такую сделку. Проверьте ссылку или попросите исполнителя отправить её ещё раз.»
2. Пользователь = исполнитель этой сделки и сделка не демо → показать карточку исполнителя (это он открыл свою ссылку).
3. У сделки уже другой клиент → **E3** «По этой ссылке уже подтверждает другой пользователь. Попросите исполнителя создать новую сделку.»
4. Сделка демо (`demo=true`) и пользователь ≠ исполнитель → **E4** «Это демонстрационная сделка исполнителя, к ней нельзя присоединиться.»
5. Статус терминальный → карточка клиента без кнопок + строка «Сделка завершена».
6. Иначе — T2: привязать клиента, отправить **C-card** (§6.4) и приветствие **S2** (одним сообщением над карточкой):
   «Исполнитель **{seller}** предлагает договорённость. Проверьте условия и подтвердите — или предложите изменения.»

### 6.4. Карточка (эталон рендера)
Функция `renderCard(deal, version, payments, role): {text, keyboard}`. Текст:
```
{статус-эмодзи} **{title}** · #{public_id}
Статус: {статус-текст для роли}

📌 {description или «—»}
🗓 {дата-время или «без даты»}
💰 {total} · предоплата {prepayment} ({процент}%)   ← если prepayment = 0: «без предоплаты»
↩️ {текст правила отмены}
{🖼 макет приложён}                                   ← только если photo

👤 Исполнитель: {seller display_name}
👤 Клиент: {имя клиента | «ещё не открыл ссылку»}
{строка оплаты: «Предоплата получена 21.09 14:03 (ссылка ЮKassa, тест)» / «Остаток 2 000 ₽ ждёт оплаты» / …}
{строка чека: «Чек приложен 22.09» / «Чек: до 9 октября»}
{🧪 ДЕМО — так видит клиент}                        ← только в демо-карточке клиента
```
Статус-тексты по ролям (`texts.status[status][role]`), например `awaiting_confirmation`: seller — «Ждём подтверждения
клиента», client — «Подтвердите условия»; `awaiting_prepayment`: seller — «Ждём предоплату {sum}», client —
«Внесите предоплату {sum}»; `paid`: seller — «Оплачено. Приложите чек», client — «Оплачено. Ждём чек от исполнителя»;
полный набор — в `texts.ts`, по одному на пару (статус, роль).
Тексты правил отмены: `free_24h` — «Отмена без потери предоплаты за 24 ч и более до срока», `free_48h` — «… за 48 ч»,
`nonrefundable` — «Предоплата не возвращается при отмене клиентом», `full_refund` — «Предоплата возвращается при любой отмене».

Карточка исполнителя с ссылкой (клиент не открыл): под текстом строка «🔗 Ссылка для клиента: `https://max.ru/{bot}?start=d_{id}`»
и кнопки: [📤 Отправить в MAX (link → `https://max.ru/:share?text={urlencoded «Подтвердите нашу договорённость: https://max.ru/…»}`)]
[📋 Скопировать ссылку (clipboard, payload = ссылка)] / [✏️ Изменить условия (open_app, payload `d_{id}`)] [🧪 Открыть как клиент (callback `dm:{id}`)] / [🚫 Отменить (callback `cn:{id}`)].

**Ответ на нажатие — всегда карточкой (правило, 22.09).** `POST /answers` в MAX **правит сообщение, на кнопке
которого нажали**. Поэтому любое нажатие кнопки на сообщении-карточке отвечается перерисованной карточкой
(`answerWithCard`): реакция на нажатие — «уже сделано», E1–E13, запрос ввода, «напоминание отправлено» — встаёт
строкой-заметкой над текстом карточки, а на время подтверждения необратимого действия клавиатура карточки
заменяется на [Да, …] [↩️ Назад] (у исполнителя при отмене — [Без причины] [↩️ Не отменять]; «Назад» снимает
ожидание причины). Остальные карточки сделки обновляются правкой (`syncCards` с `skipMid` нажатой). Текстом без
карточки бот отвечает только на кнопки вне карточки: уведомления (P2, P3, N3, N11, N13), меню, список `/deals`.
«Открыть» вне карточки (и повторный вход клиента по ссылке) присылает карточку новым сообщением вниз чата, а
старое сообщение превращается в указатель «↓ Карточка #{id} — ниже» без кнопок.

Рейл «перевод» рисует сама карточка:
- клиент, платёж `transfer/pending` — вместо строки оплаты блок «💸 Переведите **{sum}** по реквизитам и нажмите
  «✅ Я перевёл(а)»: `{реквизиты}` / 🧪 Перевод продукт не видит — его подтверждают обе стороны кнопками»;
  кнопки [✅ Я перевёл(а)] [↩️ Отмена перевода];
- клиент, `transfer/claimed` — «Вы сообщили о переводе {sum} {время}. Ждём подтверждения исполнителя», кнопок рейла нет;
- исполнитель, `transfer/pending` — «клиент выбрал перевод по реквизитам — ждём перевода»;
- исполнитель, `transfer/claimed` — [✅ Получил(а)] [❌ Не вижу перевода] прямо в карточке (P2 остаётся уведомлением,
  потому что правка карточки push-уведомления не даёт);
- `link/pending` — [Перейти к оплате] [🔄 Проверить оплату], как и раньше.

### 6.6. Ожидание ввода (`user_inputs`)
Бот запрашивает текст/файл после нажатия кнопки; ввод ждётся 30 минут:
| kind | Запрос | Валидация | Ошибка |
|---|---|---|---|
| `change_request` | «Напишите одним сообщением, что изменить (например: «давайте 15:00 и без предоплаты»).» | текст 1–500 | E5 «Слишком длинно — до 500 символов.» |
| `remarks` | «Опишите замечания одним сообщением.» | 1–500 | E5 |
| `receipt` | «Пришлите чек из «Мой налог» — фото или PDF одним сообщением.» | вложение `image` или `file` (pdf/jpg/png), ≤ 20 МБ | E6 «Нужен файл или фото. Пришлите чек вложением.» |
| `cancel_reason` | «Причина отмены одним сообщением — или нажмите «Без причины».» + кнопка [Без причины (`cn:y:{id}:none`)] | 0–300 | E5 |
Чек пересылается клиенту тем же `token` входящего вложения (`attachments[i].payload.token` для `image`/`file`); если `token`
отсутствует — скачать по `url` и загрузить через `uploadFile/uploadImage` заново. Тип и имя файла сохраняются в `receipts`.
Любое сообщение вне ожидания ввода → **S3** «Я понимаю только кнопки и команды. Откройте /deals или /new.» (и меню S1).
Просроченный ввод → **E8** «Время ожидания истекло. Нажмите кнопку ещё раз.»

## 8. Модель данных
DDL — `server/migrations/0001_init.sql` (первичен). Ключевые правила:
- `deals.public_id` — 10 символов из алфавита `A-Za-z0-9` (`nanoid` с custom alphabet); генерация с повтором при коллизии.
- Версия условий никогда не редактируется — только добавляется новая (`deal_versions`), `deals.current_version` двигается.
- В `payments` не более одного живого платежа на `(deal_id, kind)` — частичный уникальный индекс.
- `deal_events.seq` — под блокировкой строки сделки.
- `card_messages` хранит `mid` карточки каждой стороны; при неудачном `PUT /messages` (например, сообщение удалено)
  отправляем новую карточку и обновляем `mid`.
- `users.dialog_chat_id` заполняется из `bot_started.chat_id` и `message.recipient.chat_id`; `reply` в SDK шлёт по `chat_id`,
  а уведомления второй стороне — `sendMessageToUser(user_id)` (CONTRACTS §1.7) — оба варианта допустимы, используем
  `sendMessageToUser` для «чужой» стороны и `ctx.reply` для отвечающей.
- Удаление данных не предусмотрено в MVP (Won't); `dialog_removed`/`bot_stopped` → помечаем `users.dialog_chat_id = NULL`
  (уведомления перестают уходить до следующего `/start`).

## 9. Интеграции

### 9.1. Рейлы оплаты — устройство и переключение

**Кто получатель по ссылке (решение 22.09).** Рейл «ссылка» в MVP формируется в **тестовом магазине команды**, чтобы
показать интеграцию целиком: создание платежа, вебхук, статусы, отказы, истечение. В продукте этот рейл —
**собственный** эквайринг исполнителя: для ИП — его магазин ЮKassa или Т-Бизнес по API (ключи подключаются в
настройках профиля, `seller_profiles.acquiring` — следующий этап), для самозанятого — СБП-ссылка банка-партнёра или
рейл «перевод». Платформа деньги не принимает, не держит и не распределяет — поэтому она не платёжный агент (103-ФЗ),
не эскроу и не выбивает чеки за исполнителя (54-ФЗ и 422-ФЗ остаются на нём). Продукт — не приём денег, а
зафиксированная договорённость, статус у обеих сторон и доказательная квитанция. В интерфейсе рейл помечен
«🧪 Тестовый магазин ЮKassa».

Доступность кнопок в карточке клиента:
- «💳 Оплатить по ссылке» — если `PAYMENT_PROVIDER != none` **и** `seller.link_enabled` **и** сумма ≥ минимума провайдера
  (ЮKassa 1 ₽).
- «🔁 Перевести по реквизитам» — если `seller.transfer_enabled` **и** `payout_details` не пуст (иначе кнопка есть, но ответ E12).
Оба могут быть доступны одновременно; клиент выбирает при каждом платеже. Выбор фиксируется в `payments.rail`.
Смена рейла: пока платёж `pending` по ссылке, клиент может нажать «Перевести» — ссылочный платёж помечаем `canceled`
(локально; у провайдера истечёт сам) и создаём `transfer`. Обратно — так же. Один живой платёж на (сделка, вид).

**Рейл «ссылка» [тест]** — `domain/payment/rails.ts::createLinkPayment(deal, kind)`:
1. Создать запись `payments` (`pending`, `idempotence_key`), затем вызвать провайдера (§9.2/9.3).
2. Ответить клиенту обновлённой карточкой: строка «Ссылка на оплату {sum} действует до {время}» + кнопки
   [Перейти к оплате (link → `confirmation_url`)] [🔄 Проверить оплату (`pc:{id}:{payment_id}`)].
3. Подтверждение приходит вебхуком (§9.6) **или** опросом планировщика (§10.3) **или** кнопкой «Проверить оплату»
   (синхронный `GET` статуса). Любой путь ведёт в одну функцию `applyProviderStatus(payment, providerStatus)` — идемпотентную.
4. В карточке и README обязательная пометка: «оплата через **тестовый** магазин ЮKassa — реальные деньги не списываются».

**Рейл «перевод» [модель]** — клиент нажимает «Перевести по реквизитам»:
1. Создаём `payments` (`rail=transfer`, `provider=manual`, `pending`).
2. Клиенту — обновлённая карточка, в которой вместо строки оплаты блок реквизитов (§6.4): «💸 Переведите {sum} по
   реквизитам и нажмите «✅ Я перевёл(а)»:\n`{payout_details}`\n🧪 Перевод продукт не видит — его подтверждают обе
   стороны кнопками». Кнопки: [✅ Я перевёл(а) (`tr:c:{id}:{pid}`)] [↩️ Отмена перевода (`tr:x:{id}:{pid}`)].
   Отдельного сообщения P1 нет: ответ на нажатие правит саму карточку, и отдельный текст был бы тут же затёрт.
3. «Я перевёл(а)» → `claimed`, `claimed_at`; исполнителю **P2**: «{client} сообщает о переводе {sum} по #{id}. Проверьте поступление.»
   + [✅ Получил(а) (`tr:g:{id}:{pid}`)] [❌ Не вижу перевода (`tr:n:{id}:{pid}`)].
4. «Получил(а)» → `succeeded` → T9/T14. «Не вижу» → `pending`, событие `payment.not_received`, клиенту **P3**:
   «Исполнитель пока не видит перевод {sum}. Проверьте операцию и нажмите «Я перевёл(а)» ещё раз или выберите оплату по ссылке.»
5. Клиент может нажать «Я перевёл(а)» не чаще 1 раза в 10 минут, в том числе после «Не вижу» (иначе E13). Со второго «Не вижу» подряд
   клиенту уходит P3_DISPUTE: оплата по ссылке и «продукт не арбитр: спор решают стороны, хронология — в квитанции».
Никаких банковских данных продукт не запрашивает и не хранит, кроме текста реквизитов, который исполнитель сам показывает клиенту.

### 9.2. ЮKassa (тестовый магазин) — контракт: `docs/CONTRACTS.md` §2
`integrations/yookassa/client.ts`: `fetch` (без SDK), таймаут 10 с, 1 повтор при сетевой ошибке/5xx **с тем же** `Idempotence-Key`.
- Создание: `POST https://api.yookassa.ru/v3/payments`, `Authorization: Basic base64(shopId:secret)`, `Idempotence-Key: payments.idempotence_key`,
  body `{ amount: { value: '1500.00', currency: 'RUB' }, capture: true, confirmation: { type: 'redirect', return_url: PUBLIC_BASE_URL + '/pay/return?d=' + public_id }, description: 'Сделка #<id>: <title до 100 симв.>', metadata: { deal: public_id, payment: String(payments.id), kind } }`.
  Сохраняем `provider_payment_id = id`, `confirmation_url`, `expires_at = now + 1h` (срок оплаты картой), `raw`.
- Статус: `GET /v3/payments/{id}` → `status` ∈ pending | waiting_for_capture | succeeded | canceled. Маппинг: `succeeded` → `succeeded`;
  `canceled` → `canceled` (в карточке: «Оплата отменена: {cancellation_details.reason}» и кнопка создать новую ссылку);
  `pending`/`waiting_for_capture` → без изменений.
- Вебхук `POST /webhooks/yookassa`: принять, записать в `webhook_log`, ответить 200 сразу; затем **всегда** `GET /v3/payments/{object.id}`
  и применить статус из GET (уведомления не подписаны). IP-фильтр по списку CONTRACTS §2.5 — включён, при несовпадении
  логируем `warn` и всё равно делаем GET (ложных срабатываний не будет: GET — источник истины).
- Ошибки: 400/401/403 → E9 + `warn`; 429/5xx → повтор 1 раз → E9. `metadata.deal` обязан совпадать с ожидаемым — иначе `ignored:foreign`.
- Тестовые карты для README: `5555 5555 5555 4444` (успех без 3-DS), `5555 5555 5555 4477` (успех с 3-DS), `5555 5555 5555 4600` (недостаточно средств).
- `/pay/return` — статическая страница: «Спасибо! Оплата обрабатывается. Вернитесь в MAX — карточка обновится сама.» + ссылка `https://max.ru/{bot}?start=d_{id}`.

### 9.3. Т-Банк СБП (DEMO-терминал) — **не подключён (решение 22.09)**
Один реальный провайдер (ЮKassa) закрывает интеграцию целиком; второй добавил бы риск, а не проверяемую ценность.
Контракт ниже сохранён как задел — по нему рейл подключается без изменений архитектуры (`PAYMENT_PROVIDER=tbank`
сейчас не поддерживается). Контракт: `docs/CONTRACTS.md` §3
`integrations/tbank/client.ts`: `POST https://securepay.tinkoff.ru/v2/{Init|GetQr|GetState|SbpPayTest}`, JSON, `Token` по §3.2
(корневые скалярные поля + `Password` → сортировка по ключу → конкатенация значений → SHA-256 hex). Таймаут 10 с.
- `Init`: `{ TerminalKey, Amount: kopecks, OrderId: payments.idempotence_key (≤ 36 симв.), Description (≤ 140), NotificationURL: PUBLIC_BASE_URL + '/webhooks/tbank', SuccessURL: PUBLIC_BASE_URL + '/pay/return?d=…', FailURL: то же + '&fail=1', PayType: 'O', DATA: { deal: public_id }, Token }`
  → проверяем `Success === true && ErrorCode === '0'`; сохраняем `PaymentId`, `PaymentURL`.
- `GetQr`: `{ TerminalKey, PaymentId, DataType: 'PAYLOAD', Token }` → `Data` (ссылка СБП) → `qr_payload`; кнопка «Перейти к оплате» ведёт на `Data`;
  `expires_at = now + 24h` (RedirectDueDate по умолчанию).
- `GetState`: `{ TerminalKey, PaymentId, Token }` → `Status`. Маппинг: `CONFIRMED` → `succeeded`; `REJECTED`, `DEADLINE_EXPIRED`, `CANCELED`, `AUTH_FAIL`, `ATTEMPTS_EXPIRED` → `canceled`; остальные — без изменений.
- `SbpPayTest` (только `DEMO_MODE`): `{ TerminalKey, PaymentId, Token }` → затем `GetState`. Кнопка помечена 🧪 и текстом «эмуляция оплаты на DEMO-терминале».
- Вебхук `POST /webhooks/tbank`: тело JSON; проверить `Token` (все скалярные поля кроме `Token` + `Password`), сверить `TerminalKey`, `Amount` с платежом; ответить телом `OK` (text/plain, 200) всегда, кроме невалидного JSON (400); применить статус.
- Ошибки: `Success=false` → E9 с `Message` в лог; `ErrorCode='204'` (неверный токен) — отдельный лог «проверьте TBANK_TERMINAL_PASSWORD».

### 9.4. Валидация `initData` (мини-приложение) — `docs/CONTRACTS.md` §4.1
`transport/http/auth.ts`: из `X-Max-Init-Data` → пары `key=value` → проверить единственный `hash` → удалить → URL-decode
значений → сортировка по ключу → `k=v\n…` → `secret = HMAC-SHA256(key='WebAppData', msg=BOT_TOKEN)` → `hex(HMAC-SHA256(secret, строка))`
== `hash` (сравнение `timingSafeEqual`). Дополнительно: `auth_date` не старше **24 ч** (наше правило, в документации срока нет);
`user.id` → `users` (upsert имени). Ошибка → 401 `init_data_invalid`. При `MAX_MODE=off` и отсутствии токена — 401 всегда
(кроме dev-подмены). Unit-тест на примере строки из CONTRACTS §4.1.

### 9.5. Подтверждение телефона — CONTRACTS §4.2
`hash == HMAC_SHA256(authDate + phone + userId, botToken)` (hex, нижний регистр; `phone` без `+`; `userId` — из проверенного initData).
Расхождение → 400 `phone_hash_invalid`. Телефон хранится только после проверки; в карточке и PDF показывается как «+7 ••• ••• 12-34».

### 9.6. Вебхуки: общие правила
`webhook_log` — каждая доставка; обработка идемпотентна по `(provider, external_id, provider_status)`; повтор с тем же статусом →
`ignored:duplicate`. Обработка — вне HTTP-ответа (setImmediate) с try/catch и записью `result`. Никаких редиректов.

### 9.7. Работа с MAX Bot API — правила для кода (из CONTRACTS §1)
- Отправка: `bot.api.sendMessageToUser(userId, text, { format: 'markdown', attachments })`; редактирование карточки: `bot.api.editMessage(mid, { text, attachments, format })`;
  ответ на кнопку: `ctx.answerOnCallback({ message: { text, attachments, format } })` — обновляет то же сообщение.
- Клавиатура: `Keyboard.inlineKeyboard([[…]])` из `@maxhub/max-bot-api`; кнопки `Keyboard.button.callback/link/clipboard/openApp`.
  Ограничения: ≤ 7 кнопок в ряду (≤ 3 для `link`/`open_app`), ≤ 30 рядов. `open_app(text, webApp = MAX_BOT_USERNAME, undefined, payload)`.
- Вложения PDF/чек: `bot.api.uploadFile({ source: '/tmp/<name>.pdf' })` (путь, не Buffer — иначе имя файла UUID) → `attachments: [file.toJson()]`;
  SDK сам повторяет при `attachment.not.ready` (3 попытки).
- Лимиты: очередь отправки с троттлингом ≤ 2 сообщения/с на чат (`integrations/max/notify.ts`), 429 → пауза 1 с и повтор (до 3).
- Текст ≤ 4000 символов; карточка проектируется ≤ 1200.
- Ошибки SDK — `MaxError {status, code, description}`; 401 при старте → `exit(1)` с текстом «неверный токен».

## 10. Планировщик напоминаний

### 10.1. Принцип
Напоминания **материализуются** при каждом переходе (`domain/reminder/plan.ts::planReminders(deal)`): все `pending` этой
сделки → `cancelled`, затем создаётся набор для нового статуса. `dedupe_key = <deal_id>:<kind>:<status_changed_at ISO>` —
уникальный индекс защищает от дублей при повторном планировании. Тик планировщика (30 с) берёт `pending` с `due_at <= now`
(`FOR UPDATE SKIP LOCKED`, порциями по 50), отправляет, ставит `sent`/`failed` (3 попытки, потом `failed`). Отправка
пропускается (status `cancelled`, `last_error='state_changed'`), если статус сделки уже не тот, для которого создано напоминание.

### 10.2. Набор напоминаний
| kind | Статус сделки | Кому | Когда | Текст |
|---|---|---|---|---|
| `client_not_opened` | awaiting_confirmation, клиент не открыл | seller | +24 ч от создания/версии | «Клиент ещё не открыл карточку #{id}. Отправьте ссылку ещё раз или напомните ему.» + [Отправить в MAX] [Скопировать ссылку] |
| `confirmation_expired` | awaiting_confirmation / changes_requested | system | +72 ч | выполняет T8 |

### 10.3. Прочие задания планировщика
- `payments-poll` (каждый тик): платежи `rail=link`, `status=pending`, `created_at < now − 30 с`, `expires_at > now` → опрос статуса
  провайдера (не чаще 1 раза в 60 с на платёж, поле `updated_at`); истёкшие → `expired` + карточка «Ссылка истекла» с кнопкой «Новая ссылка».
- `expire` — обрабатывается через напоминание `confirmation_expired` (единый механизм).
- Защита: тик не стартует, пока предыдущий не завершён; ошибки задания логируются и не роняют процесс.

## 11. Квитанция PDF

Генерация: `pdfkit` 0.20.2, шрифт `node_modules/dejavu-fonts-ttf/ttf/DejaVuSans.ttf` (+ `-Bold`) — кириллица. A4, поля 20 мм.
Имя файла: `Квитанция_{public_id}.pdf`. Формируется при T15 (и при отмене/отказе — по запросу кнопкой «Квитанция PDF»).
Содержимое (сверху вниз):
1. Заголовок: «Квитанция о сделке №{public_id}» · «Сформировано ботом «Договорились» в MAX · {дата-время}».
   Демо: диагональный водяной знак «ДЕМО» серым 15 % и строка «Демонстрационная сделка: обе стороны — один пользователь».
2. Стороны: Исполнитель — {display_name}, MAX id {user_id}, {телефон маской, если подтверждён}; Клиент — {имя}, MAX id {user_id}.
3. Условия (текущая версия): название, описание, дата/время, сумма, предоплата, правило отмены, «Версия {n} от {дата}».
   Если версий > 1 — таблица «История условий»: версия · дата · сумма · предоплата · дата подтверждения клиентом.
4. Подтверждения: «Условия подтверждены клиентом {дата-время} (MAX id …)», «Работа отмечена выполненной {…}», «Принята клиентом {…}».
5. Платежи: таблица kind · сумма · рейл (ссылка ЮKassa **тест** / СБП Т-Банк **DEMO** / перевод по реквизитам, подтверждён сторонами) · id провайдера · дата.
   Итого оплачено; остаток.
6. Чек: «Чек НПД приложен исполнителем {дата}» / «Чек не приложен» / «Чек не требуется (режим без чека)».
7. Статус и завершение: «Сделка закрыта {дата}» / «Отменена {кем} {дата}: {причина}; предоплата: {возврат ожидается/не возвращается}».
8. Подвал: «Документ фиксирует договорённость и подтверждения сторон в MAX; не является кассовым чеком или чеком НПД.
   Тестовые платежи: реальные деньги не движутся.» + QR (Could) с ссылкой на бота.
Отправка: `uploadFile({source: путь})` → `sendMessageToUser` обеим сторонам с текстом N14. Временный файл удаляется после отправки.

## 12. Демо-режим «Открыть как клиент»

Цель: эксперт проходит сценарий целиком с одного аккаунта. Реализация:
- Включается `DEMO_MODE=true`. Кнопка 🧪 «Открыть как клиент» есть в карточке исполнителя, пока `client_user_id IS NULL`.
- Нажатие → `deals.demo = true`, `client_user_id = seller_user_id`, событие `demo.opened`, затем стандартный T2: в **тот же чат**
  отправляется клиентская карточка с префиксной строкой «🧪 **ДЕМО — так видит клиент**» и клиентскими кнопками.
  Все клиентские действия обрабатываются обычными обработчиками; `actor_role = 'client_demo'`.
- Уведомления «второй стороне» в демо тоже приходят в этот чат — с префиксом «🧪 (клиенту)» / «🧪 (исполнителю)», чтобы
  экспериментатор видел обе стороны. Две карточки (исполнителя и «клиента») живут в одном чате и обновляются каждая.
- Помечено: в карточках, в списке сделок (бейдж «демо»), в PDF (водяной знак), в README (раздел «Тестовые данные»).
- Реальный клиент не может присоединиться к демо-сделке (E4). Обратной операции («сделать реальной») нет — создать новую.
- Кнопка «🧪 Попробовать на демо-сделке» в меню S1 создаёт сделку по шаблону `beauty`: «Маникюр с покрытием», завтра 14:00,
  2 500 ₽, предоплата 500 ₽, `free_24h`, и сразу открывает её как клиент.
- При `DEMO_MODE=false` кнопки скрыты, а обработчики отвечают E1.

## 13. Диплинки и payload

| Ссылка | Формат | Где приходит |
|---|---|---|
| Клиенту в сделку | `https://max.ru/{bot}?start=d_{public_id}` | `bot_started.payload = 'd_<id>'` (≤ 128 симв.) |
| Мини-приложение, экран | `https://max.ru/{bot}?startapp=new` \| `deals` \| `settings` \| `d_{public_id}` | `initDataUnsafe.start_param` (только `A-Za-z0-9_-`, ≤ 512) |
| Шеринг | `https://max.ru/:share?text={urlencoded}` | экран «Отправить в MAX» |
Payload `d_<id>`: `^d_[A-Za-z0-9]{10}$`; всё иное в `?start=` — игнорируется (меню S1). Ссылка — секрет-возможность (unguessable id),
других прав доступа к ней нет; повторное открытие тем же клиентом — идемпотентно.
Callback payload кнопок: `^[a-z]{2}(:[a-z])?:[A-Za-z0-9]{10}(:[A-Za-z0-9]+)?$`, коды: `cf` подтвердить, `cr` предложить изменения, `dc` отказаться, `dc:y` подтвердить отказ,
`pl` оплата по ссылке, `pt` перевод, `tr:c|g|n|x` (перевёл / получил / не вижу / отмена рейла), `pc` проверить оплату, `pe` эмулировать (tbank demo), `nl` новая ссылка, `dn` выполнено, `ac` принять,
`rm` замечания, `fx` исправлено, `rc` приложить чек, `nc` закрыть без чека, `nc:y` подтвердить закрытие без чека, `cn` отменить, `cn:y` подтвердить отмену (`cn:y:<id>:none` — без причины), `ka` оставить как есть,
`rs` напомнить клиенту, `dm` демо, `op` открыть карточку, `pdf` квитанция, `help`. Кнопка с неизвестным payload → E1.

## 14. Обработка ошибок и краевые случаи (обязательные тесты)
1. Двойное нажатие «Подтверждаю» → второй ответ «уже подтверждено», без второго события.
2. Повторный вебхук `payment.succeeded` → `ignored:duplicate`, без второго перехода.
3. Вебхук с чужим `metadata.deal` → `ignored:foreign`.
4. `PUT /messages` вернул `success:false` (карточка удалена) → новая карточка, `mid` обновлён.
5. Клиент открыл ссылку дважды / с другого устройства → одна привязка.
6. Исполнитель открыл собственную ссылку → карточка исполнителя, не клиента.
7. Ссылка на оплату истекла → статус `expired`, кнопка «Новая ссылка» создаёт новый платёж с новым `Idempotence-Key`.
8. Провайдер недоступен (таймаут) → E9, платёж `canceled` локально, кнопка доступна снова.
9. Сообщение с вложением без ожидания ввода → S3.
10. Файл чека > 20 МБ или не image/pdf → E6.
11. `scheduled_at` в прошлом при создании → 400 `validation` с текстом поля.
12. Пользователь заблокировал бота (`bot_stopped`) → уведомления ему помечаются `no_chat`, сделка живёт.
13. Рестарт процесса во время ожидания ввода → состояние в `user_inputs`, ввод принимается.
14. Два экземпляра с одним токеном → документировано в README (запрещено); код не защищает.
15. Нагрузка: 20 сделок × 2 карточки обновляются за ≤ 10 с (троттлинг 2 msg/с на чат — чаты разные).

## 17. Нефункциональные требования
- Безопасность: секреты только в env; initData/HMAC проверки; `timingSafeEqual`; входные данные — zod; SQL — только параметризованные;

- Тесты (vitest): машина состояний (таблица §5.2 полностью), правило отмены §5.3, `initData` (пример из CONTRACTS), Т-Банк `Token`
  (пример из CONTRACTS §3.2 → ожидаемый hex), разбор статусов ЮKassa/Т-Банк, планирование напоминаний по датам (фиксированное «сейчас»).
- Совместимость: MAX iOS/Android/desktop/web; мини-приложение — ширина 360–430 px и desktop; без внешних CDN, кроме `st.max.ru` (Bridge).

## 19. Ответы на вопросы, которые возникнут у читателя впервые
- **Где взять ник бота?** `GET /me` при старте; до этого — `MAX_BOT_USERNAME` пуст, диплинки не строятся; при `MAX_MODE=off` ссылки показываются с `{bot}` = «bot».
- **Что, если у клиента нет диалога с ботом?** Ссылка `?start=` его создаёт — это единственный способ (бот не пишет первым).
- **Почему карточка — два сообщения, а не одно общее?** У бота нет общего чата сторон (создать чат он не может); у каждой стороны своё сообщение с одинаковым состоянием.
- **Почему статус обновляем и на месте, и отдельным сообщением?** Правка на месте не даёт push-уведомления; короткое сообщение — даёт.
- **Почему long polling локально и webhook на VPS?** Webhook требует HTTPS:443 с доверенным сертификатом; локально его нет. Один токен — один экземпляр (SDK стирает подписки).
- **Как эксперт проверит одним аккаунтом?** Демо-режим §12 плюс кнопка «Попробовать на демо-сделке» в меню.
- **Что с деньгами?** Продукт их не касается (§9.1). Эквайринг — тестовые среды. Это сказано в README, в презентации и в карточке.
- **Что делать, если MAX UI не собирается с нашей версией React?** MAX UI требует ровно `react 19.2.8` — зафиксировано; при конфликте — свои компоненты на токенах из `docs/DESIGN.md`, запись в ДОПУЩЕНИЯ.
- **Сертификат Минцифры?** `certs/README.md`; без него `platform-api2.max.ru` не откроется из Node в Docker — это первая проверка в ЗАДАЧА_01.
- **Часовой пояс?** Всё показываем в Europe/Moscow; храним UTC; напоминания по МСК.
- **Как мини-приложение привязывается к боту на хакатоне?** URL `PUBLIC_BASE_URL/app/` отправляет Екатерина через форму организаторов
  (https://sbor-ssylok-dlya-mini-prilojeniy.testograf.ru/, из письма с токеном) после деплоя на VPS. Кабинета business.max.ru у команды нет,
  поэтому URL должен быть стабильным с первой подачи; до привязки сценарий проходится через демо-сделку из меню (§12) и команду `/new`.
- **Что делать исполнителю с «Предложить изменения», пока мини-приложение не привязано?** Кнопки «Оставить как есть» и «Отменить» работают
  всегда; редактирование условий — только через мини-приложение (Must) — либо новая сделка. Текстовое редактирование в боте — Won't.
- **Как узнать, какое событие приходит при повторном нажатии диплинка?** Проверить в шаге 0 ЗАДАЧА_01 с логированием `DEBUG=max:*`;
  обработчик принимает оба источника (§6.3).
- **Что считать «основным сценарием» для жюри?** Создать сделку → отправить/открыть как клиент → подтвердить → предоплата (перевод «перевёл/получил» или тестовая ссылка) → выполнено → принято → остаток → чек → квитанция PDF обеим сторонам. Порядок проверки — README §«Сценарий проверки».
