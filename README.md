# Договорились — подтверждённая договорённость в чате MAX

Хакатон MAX 2026 · трек «Эффективный бизнес» · команда **Pulsar** (Алексанян Екатерина, Качалкина Александра, Колесников Павел).

## 1. Назначение решения

Самозанятый или микро-ИП фиксирует договорённость с клиентом карточкой в чате MAX (что / когда / сколько / предоплата /
правило отмены), клиент подтверждает её одной кнопкой, предоплата и остаток проходят по выбранному рейлу, статус
обновляется у обеих сторон, бот напоминает о визите, оплате и чеке, по завершении обе стороны получают чек и квитанцию PDF.
Деньги идут напрямую исполнителю — сервис их не принимает и не хранит реквизиты карт.
Обоснование, аудитория, цитаты пользователей — `docs/КОНЦЕПЦИЯ.md`; спецификация — `docs/SPEC.md`; масштабирование — `docs/SCALING.md`.

## 2. Основной пользовательский сценарий

1. Исполнитель: `/start` → «Новая сделка» → мини-приложение: шаблон, что, когда, сумма, предоплата, правило отмены → «Создать».
2. Бот выдаёт карточку и ссылку `https://max.ru/<бот>?start=d_<id>`; исполнитель отправляет её клиенту в существующий чат.
3. Клиент открывает ссылку → карточка → «Подтверждаю» → вносит предоплату (ссылка эквайринга **[тест]** или перевод по реквизитам
   с подтверждением «перевёл / получил»).
4. Исполнитель: «Выполнено» → клиент: «Принимаю» → остаток тем же способом.
5. Исполнитель прикладывает чек из «Мой налог» → обе стороны получают чек и квитанцию PDF. Статусы обеих сторон обновляются на месте.
Демо-режим «🧪 Открыть как клиент» позволяет пройти всё одним аккаунтом (помечен в интерфейсе и в квитанции).

## 3. Состав и архитектура решения

(заполняется по ходу; каркас — `docs/SPEC.md` §4)
- `server/` — бот MAX (SDK `@maxhub/max-bot-api`), HTTP (Fastify: `/api`, `/webhooks`, `/app`), домен, планировщик, PDF.
- `webapp/` — мини-приложение (React 19 + MAX UI), собирается в `webapp/dist`, раздаётся сервером по `/app/`.
- `db` — Postgres 16, миграции `server/migrations/*.sql`.
- Схема компонентов и слоёв — `docs/SPEC.md` §4.1–4.2.

## 4. Запуск одной командой (Docker)

```bash
cp .env.example .env          # заполнить MAX_BOT_TOKEN (и при необходимости ключи провайдера)
docker compose up --build     # сервис на http://localhost:8080 , БД внутри compose
```
Замер сборки из чистого клона: **(заполняется по ходу: дата, машина, время `docker compose build` без учёта pull базовых образов)**.
Предварительно измерено вне Docker (20.09.2026): `npm ci` — 29 с, `npm run build` — 5 с.
Проверка: `curl http://localhost:8080/healthz` → `{"ok":true,...}`; `curl http://localhost:8080/readyz` → `{"ok":true}`.
Продакшн с HTTPS (VPS): `docker compose --profile prod up -d --build` (Caddy выпускает сертификат для `PUBLIC_HOST`).

> Важно: к одному токену бота может быть подключён только один экземпляр. Локальный запуск с боевым токеном в режиме
> `MAX_MODE=polling` **удалит webhook-подписку** развёрнутого экземпляра. Для проверки сборки без бота используйте `MAX_MODE=off`.

## 9. Работа с данными

(заполняется по ходу) Хранятся: пользователи MAX (id, имя, chat_id диалога, телефон — только после HMAC-проверки, маской в интерфейсе),
сделки и версии условий, платежи (id провайдера, статусы — без реквизитов карт), события, напоминания, вложения-чеки (токены MAX).
Схема — `server/migrations/0001_init.sql`. Реквизиты для перевода — текст, который исполнитель сам показывает клиенту.

## 10. Порядок работы с тестовыми данными

(заполняется по ходу) Тестовые карты ЮKassa: `5555 5555 5555 4444` (успех), `5555 5555 5555 4477` (успех, 3-DS), `5555 5555 5555 4600`
(недостаточно средств); срок — любая будущая дата, CVC — любой. Т-Банк: DEMO-терминал, оплата эмулируется кнопкой 🧪.
Демо-сделка: кнопка «🧪 Попробовать на демо-сделке» в `/start`.

## 11. Пошаговый сценарий проверки

(заполняется по ходу; черновик)
1. Откройте бота `https://max.ru/<ник>` → `/start` → «🧪 Попробовать на демо-сделке» (или «Новая сделка» → заполните форму).
2. В карточке «ДЕМО — так видит клиент» нажмите «Подтверждаю» → «Перевести по реквизитам» → «Я перевёл(а)».
3. В карточке исполнителя нажмите «Получил(а)» → статус «Запланировано» у обеих карточек.
4. «Выполнено» → в клиентской карточке «Принимаю» → остаток: «Оплатить по ссылке» (тестовая карта) или перевод.
5. «Приложить чек» → отправьте любое фото/PDF → обе карточки «Закрыто», в чат приходит квитанция PDF.
6. Для двух аккаунтов: шаг 2 выполняется со второго аккаунта по ссылке из карточки.

## 13. Известные ограничения

- Оплата по ссылке — тестовые среды провайдеров; рейл «перевод» подтверждается сторонами вручную; чек НПД прикладывается вручную.
- Бот не может написать клиенту первым: клиент должен один раз открыть ссылку.
- Один токен — один экземпляр (см. §4). Long polling локально; webhook — на VPS.
(дополняется по ходу)

## 14. Остановка и перезапуск

```bash
docker compose down            # остановить (данные БД сохраняются в volume pgdata)
docker compose up -d           # запустить снова
docker compose down -v         # остановить и удалить данные
docker compose logs -f app     # логи сервиса
```

## 15. Возможности MAX сверх минимума (платформенный бонус)

(заполняется по ходу) Диплинк-приглашение второго участника → мини-приложение с серверной валидацией `initData` → живая карточка
через `POST /answers` у обеих сторон → шеринг через `https://max.ru/:share` / `shareMaxContent` → `clipboard`-кнопка. См. `docs/SPEC.md` §16.

## 16. Собственный API

Внешнего API нет: HTTP-интерфейс `/api` — внутренний, для мини-приложения (авторизация по `initData`), `openapi.yaml` и `DATA-API.yaml`
не подаются (регламент: собственный API не обязателен).
