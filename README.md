## 1. Назначение решения

Самозанятый или микро-ИП фиксирует договорённость с клиентом карточкой в чате MAX (что / когда / сколько / предоплата /
правило отмены), клиент подтверждает её одной кнопкой, предоплата и остаток проходят по выбранному рейлу, статус
обновляется у обеих сторон, бот напоминает о визите, оплате и чеке, по завершении обе стороны получают чек и квитанцию PDF.
Деньги идут напрямую исполнителю — сервис их не принимает и не хранит реквизиты карт.

**Кто получатель по ссылке.** Рейл «ссылка» в этой версии формируется в **тестовом магазине ЮKassa команды** — так
видна интеграция целиком: создание платежа, вебхук, статусы, отказы, истечение. В продукте этот рейл — собственный
эквайринг исполнителя (для ИП — его магазин ЮKassa или Т-Бизнес по API, для самозанятого — СБП-ссылка банка или
рейл «перевод»). Платформа деньги не принимает, не держит и не распределяет: она не платёжный агент (103-ФЗ), не
эскроу и не выбивает чеки за исполнителя (54-ФЗ и 422-ФЗ остаются на нём). Продукт — зафиксированная
договорённость, статус у обеих сторон и доказательная квитанция. Подробно — `docs/SPEC.md` §9.1.

Обоснование, аудитория, цитаты пользователей — `docs/КОНЦЕПЦИЯ.md`; спецификация — `docs/SPEC.md`; масштабирование — `docs/SCALING.md`.

## 2. Основной пользовательский сценарий

1. Исполнитель: `/start` → «Новая сделка» → мини-приложение: шаблон, что, когда, сумма, предоплата, правило отмены → «Создать».
2. Бот выдаёт карточку и ссылку `https://max.ru/<бот>?start=d_<id>`; исполнитель отправляет её клиенту в существующий чат.
3. Клиент открывает ссылку → карточка → «Подтверждаю» → вносит предоплату (ссылка эквайринга **[тест]** или перевод по реквизитам
   с подтверждением «перевёл / получил»).
4. Исполнитель: «Выполнено» → клиент: «Принимаю» → остаток тем же способом.
5. Исполнитель прикладывает чек из «Мой налог» → обе стороны получают чек и квитанцию PDF. Статусы обеих сторон обновляются на месте.
Демо-режим «🧪 Открыть как клиент» позволяет пройти всё одним аккаунтом (помечен в интерфейсе и в квитанции).

Вокруг основного сценария:
- **Правка условий.** Клиент «✏️ Предложить изменения» → исполнитель «✏️ Изменить условия» (мини-приложение, та же
  форма) → клиент получает версию 2 со списком изменений («срок → …; сумма → …») и подтверждает именно её; кнопка
  прежней версии уже не срабатывает.
- **Другое время.** «Предложить изменения» даёт клиенту выбор: «🗓 Другое время» (календарь на 30 дней, слоты по 30
  минут с 08:00 до 21:30 МСК, занятые часы исполнителя недоступны с учётом длительности визита) или «Написать текстом».
  Исполнитель получает «✅ Принять {время}» — одно нажатие создаёт новую версию условий, клиент подтверждает её как
  обычно. Если время успели занять, предложение снимается, обе стороны получают понятный следующий шаг.
- **Напоминания.** За 30 минут до визита — обеим сторонам; каждое утро в выбранное время (по умолчанию 08:00 МСК,
  06:00–12:00 или «выключено» в «Настройках») — исполнителю расписание на сегодня, если есть записи; плюс напоминания
  о предоплате, приёмке, остатке и чеке.
- **«📁 Мои сделки»** — вкладки «Я исполнитель» / «Я клиент», расписание по дням (−7…+21) и список с фильтрами;
  в чате то же кратко — `/deals`.
- **Навигация в мини-приложении** — нижняя панель «Новая · Сделки · Настройки» на всех экранах; «назад» MAX ведёт по
  пройденным экранам, а на экране, с которого приложение открыли, закрывает его.
- **Экран сделки** (строка «Моих сделок», «К сделке» на «Готово», `startapp=deal_<id>`) — условия, стороны, деньги,
  хронология, история версий, документы и ровно те действия, что на карточке в чате (они читаются из её клавиатуры).
  Действие с экрана идёт тем же путём, что кнопка в чате: карточки обеих сторон обновляются, вторая сторона получает
  уведомление. Исполнитель может приложить чек файлом прямо с экрана. Оплата остаётся в чате.
- **«Мои услуги»** (в «Настройках») — сохранённые условия: название, цена, длительность, предоплата, правило отмены.
  В «Новой сделке» блок «Выбрать услугу» подставляет всё, кроме даты; заполненную форму можно «Сохранить как услугу».
  Клиент список услуг не видит: это инструмент исполнителя, не витрина.
- **Надёжность и оценка.** В «Настройках» исполнитель видит показатели из фактов своих сделок: закрыто, без споров,
  чек в срок, отмены с его стороны, средняя оценка. По переключателю (по умолчанию выключен) клиент видит в карточке
  строку «12 сделок, 98 % без споров», если закрытых сделок 3 и больше. После закрытия клиенту приходит просьба оценить
  работу 1–5 с необязательным комментарием; оценку видит только исполнитель, публичного рейтинга нет.
- **«🔁 Повторить»** у завершённой сделки — те же условия без даты; «Тот же клиент» отправляет карточку ему сразу,
  без ссылки.

## 3. Состав и архитектура решения

Один процесс Node.js (бот + HTTP + планировщик) и один Postgres. Второго процесса нет намеренно: запуск одной
командой и меньше точек отказа. Схема компонентов — `docs/SPEC.md` §4.1.

```
server/src/
  index.ts                 старт: конфиг → БД (ретрай) → миграции → HTTP → бот → планировщик
  config.ts                чтение и валидация env (zod), exit(1) с понятным текстом
  texts.ts                 ВСЕ тексты бота и уведомлений (SPEC §6) — одно место
  types.ts errors.ts logger.ts
  transport/bot/            обработчики MAX: start, menu, deal, payment, input; карточки, клавиатуры, уведомления
  transport/http/           Fastify: /api для мини-приложения, /pay/return, статика /app/, валидация initData
  domain/                   вся бизнес-логика: deal/{state-machine,rules,service}, payment, reminder, receipt,
                            money, time, ids, templates
  integrations/max/         gateway — единственный выход в Bot API: троттлинг, ретраи, типизированные ошибки
  db/                       pool, migrate, repos/* — единственное место, где есть SQL
  scheduler/                тик 30 с: напоминания, истечение срока подтверждения
webapp/src/                 мини-приложение: bridge, api, nav (история «назад»), экраны New / Done / Deals / Deal / Settings,
                            свои компоненты на токенах MAX UI (панель разделов, лист снизу, тост, сегмент-контрол)
server/migrations/*.sql     схема БД, мини-раннер в db/migrate.ts
```

Правило слоёв (проверяется на ревью): `transport` не содержит бизнес-логики — только разбор входа, вызов
`domain` и отрисовка ответа; `domain` не знает ни про SDK MAX, ни про HTTP; `integrations` — тонкие клиенты.
Все переходы сделки идут через одну функцию `canTransition` и выполняются в транзакции с `SELECT … FOR UPDATE`.

## 4. Запуск одной командой (Docker)

```bash
cp .env.example .env          # заполнить MAX_BOT_TOKEN (и при необходимости ключи провайдера)
docker compose up --build     # сервис на http://localhost:8080 , БД внутри compose
```
**Замер сборки из чистого клона (20.09.2026):** `docker compose build` — **43 секунды**.
Машина: macOS 26, Docker 29.5.2 в colima, VM 2 vCPU / 2 ГБ (те же ресурсы, что у целевого VPS Timeweb Cloud-40).
Базовые образы `node:22-alpine` и `postgres:16-alpine` скачаны заранее (`docker pull`), как и будет у проверяющего.
Лимит регламента — 5 минут. Вне Docker из чистого клона: `npm ci` — 39 с на холодном кеше npm и 2 с на тёплом,
`npm run build` — 6 с, `npm test` — 637 тестов за ~5,5 мин (27.09; сквозные ограничены настоящим троттлингом 2 сообщения/с).

Проверка после запуска:
```bash
curl http://localhost:8080/healthz   # {"ok":true,"service":"dogovorilis","mode":"polling"}
curl http://localhost:8080/readyz    # {"ok":true,"db":true,"bot":true}
curl -i http://localhost:8080/api/me # 401 {"error":{"code":"init_data_invalid",...}} — так и должно быть без initData
```
Продакшн с HTTPS (VPS): `docker compose --profile prod up -d --build` — Caddy выпускает сертификат
Let's Encrypt для `PUBLIC_HOST`. Разворачивается не руками: `deploy/bootstrap-server.sh` готовит сервер,
`deploy/deploy.sh` выкатывает код и проверяет результат. Runbook (обновление, логи, откат, бэкап,
диагностика «бот молчит», управление сервером через API Timeweb) — `deploy/README.md`.

**Развёрнуто 21.09.2026** на Timeweb Cloud (зона `spb-3`, Ubuntu 24.04, 2 × 3.3 ГГц / 4 ГБ / 50 ГБ NVMe).
Проверено на сервере: `/healthz` и `/readyz` (`{"ok":true,"db":true,"bot":true}`) — 200, `/app/` — 200,
сертификат Let's Encrypt, обе миграции применились на чистой базе, бот работает в режиме `webhook`
и его подписка зарегистрирована у MAX. Процесс переживает падение: после `kill -9` контейнер поднялся
сам (`restart: unless-stopped`, `RestartCount=1`) и заново зарегистрировал подписку.

**Сертификат Минцифры обязателен.** `platform-api2.max.ru` предъявляет цепочку Russian Trusted Sub CA → Russian
Trusted Root CA, которой Node не доверяет по умолчанию (в его наборе корней нет ни одного российского). Файл
`certs/russian_trusted_bundle.pem` лежит в репозитории (публичные сертификаты), образ запускается с
`NODE_EXTRA_CA_CERTS`. Как собрать заново — `certs/README.md`.

> Важно: к одному токену бота может быть подключён только один экземпляр. Локальный запуск с боевым токеном в режиме
> `MAX_MODE=polling` **удалит webhook-подписку** развёрнутого экземпляра — сервер вернёт её сам в течение 5 минут
> (сторож подписки, `deploy/README.md` §5), но всё это время бот в MAX молчит. Для проверки сборки без бота используйте `MAX_MODE=off`.

## 6. Порты

- `8080` — сервис (HTTP: API, вебхуки, мини-приложение). Настраивается `PORT`. Публикуется **только на
  `127.0.0.1`** хоста (`"127.0.0.1:${PORT:-8080}:8080"` в `compose.yaml`): локально `http://localhost:8080`
  работает как раньше, а на сервере порт 8080 снаружи закрыт — весь трафик идёт через Caddy (80/443), который
  ходит к `app:8080` по внутренней сети compose. `X-Forwarded-For` приложение принимает только от прокси
  с loopback и из частных сетей (Caddy в сети Docker), поэтому подделать IP клиента снаружи нельзя.
  `/webhooks/*` ограничены 600 запросами в минуту с одного IP (`@fastify/rate-limit`), сверх — `429`.
- `5432` — Postgres внутри сети compose (наружу не публикуется).
- `80/443` — Caddy (только профиль `prod`).

## 9. Работа с данными

Хранятся: пользователи MAX (id, имя, chat_id диалога, телефон — только после HMAC-проверки, маской в интерфейсе),
сделки и версии условий, платежи (id провайдера, статусы — без реквизитов карт), события, напоминания, вложения-чеки (токены MAX).
Схема — `server/migrations/0001_init.sql` и `0002_payments_provider.sql` (применяются автоматически при старте). Реквизиты для перевода — текст, который исполнитель сам показывает клиенту.
Доставки вебхуков пишутся в `webhook_log`; у чужих и битых хранится только сводка (событие, id объекта, размер), а не тело.

## 10. Порядок работы с тестовыми данными

Всё смоделированное помечено в интерфейсе — таблица «реальное vs смоделированное» в `docs/SPEC.md` §18.

- **Демо-сделка** — «🧪 Попробовать» → «Демо: пройти одному» в меню `/start` (или в `/new`). Данные-пример: «Маникюр с покрытием»,
  завтра 14:00, 2 500 ₽, предоплата 500 ₽. Помечена: префикс «🧪 ДЕМО — так видит клиент» в карточке,
  бейдж «демо» в списке, диагональный водяной знак «ДЕМО» в квитанции PDF.
- **Реквизиты для перевода** у демо-сделки — заведомо нерабочие и подписаны «(данные-пример)».
- **Напоминания в демо ускорены**: «примите работу» (клиенту) и «не забудьте чек» (исполнителю) приходят через
  2 минуты вместо суток, с пометкой «🧪 в демо — ускорено». Остальные сроки — как в настоящей сделке (`docs/SPEC.md` §10.2).
- **Перевод по реквизитам** — смоделированный рейл: факт перевода подтверждают обе стороны кнопками,
  денег продукт не касается. Так и написано в сообщении клиенту.
- **Чек** — любой файл (фото или PDF): в этой версии он только прикладывается и пересылается клиенту,
  фискального смысла не несёт, квитанция об этом прямо говорит.
- **Оплата по ссылке** — настоящий API ЮKassa, но **тестового магазина**: запросы, вебхуки и статусы
  реальные, деньги не движутся. Включается `PAYMENT_PROVIDER=yookassa` с ключами тестового магазина.
  В сообщении со ссылкой сразу подсказано, что вводить: «🧪 Тестовый магазин: подойдёт карта 5555 5555 5555 4444,
  любая будущая дата, любой CVC; деньги не списываются». После оплаты строка в карточке: «Предоплата получена
  26.09 17:24 (МСК) — ссылка ЮKassa, тестовый магазин, деньги не списывались».

  Тестовые карты (срок — любая будущая дата, CVC и код 3-DS — любые цифры):

  | Карта | Что произойдёт |
  |---|---|
  | `5555 5555 5555 4444` | оплата пройдёт сразу, без 3-DS → «Предоплата получена», сделка идёт дальше |
  | `5555 5555 5555 4477` | оплата пройдёт после экрана 3-DS |
  | `5555 5555 5555 4600` | отказ «недостаточно средств» → в карточке причина и кнопка «🆕 Новая ссылка» |
  | `5555 5555 5555 4543` | отказ «истёк срок действия карты» |

  Ссылка живёт **1 час** (срок оплаты картой у ЮKassa). После этого платёж переходит в `expired`,
  в карточке появляется «Ссылка на оплату … истекла» и кнопка «🆕 Новая ссылка» — тупика нет.
- **Т-Банк СБП не подключён** (решение команды). Кнопка «💳 Оплатить по ссылке» при `PAYMENT_PROVIDER=none`
  честно отвечает «Оплата по ссылке не подключена».

## 11. Пошаговый сценарий проверки

Проверяется **одним человеком** за пару минут. Бот: **https://max.ru/t713_hakaton_max_bot**

### Вариант А — одним аккаунтом (демо-режим)
1. Откройте бота по ссылке выше и нажмите «Начать» (или отправьте `/start`).
2. В меню нажмите **«🧪 Попробовать»**, затем **«Демо: пройти одному»**. В чат придут **две карточки**: ваша (исполнителя) и
   помеченная «🧪 ДЕМО — так видит клиент». Обе относятся к одной сделке и обновляются каждая.
3. В **демо-карточке** нажмите «✅ Подтверждаю» → статус меняется у обеих карточек, вам приходит уведомление.
4. Предоплата — **любым из двух способов**:
   - «💳 Оплатить по ссылке» → кнопка «Перейти к оплате» → карта `5555 5555 5555 4444`, срок — любая
     будущая дата, CVC — любой. После оплаты вернитесь в MAX: карточка обновится сама (на сервере — вебхуком,
     локально — опросом в течение минуты). Не хотите ждать — нажмите «🔄 Проверить оплату».
   - «🔁 Перевести по реквизитам» → реквизиты появятся прямо в демо-карточке → «✅ Я перевёл(а)», затем шаг 5.
5. Если платили переводом — в **своей** карточке (или в пришедшем сообщении) нажмите «✅ Получил(а)».
   Так или иначе сделка переходит в «Запланировано».
6. В **своей** карточке нажмите «✔️ Выполнено» → в демо-карточке «👍 Принимаю».
7. Остаток — тем же способом (по ссылке или переводом).
8. «📎 Приложить чек» → отправьте **любое фото или PDF** одним сообщением. Если помедлить на шагах 6 или 8 дольше
   2 минут, придёт напоминание с кнопкой «Открыть» и пометкой «🧪 в демо — ускорено».
9. Итог: обе карточки в статусе «✅ Закрыто», в чат приходит **квитанция PDF** (с водяным знаком «ДЕМО»)
   и пересланный чек.

### Вариант Б — двумя аккаунтами (настоящий клиент)
1. С первого аккаунта создайте сделку: в меню **«🧪 Попробовать» → «Сделка-пример: позвать клиента»** — это
   настоящая сделка с условиями-примером, создаётся прямо из чата за одно нажатие. Свои условия — через
   «➕ Новая сделка» (мини-приложение).
2. В карточке нажмите «📤 Отправить в MAX» (откроется выбор чата с готовым текстом «Подтвердите нашу
   договорённость: {что}, {когда} (МСК)» и одной ссылкой) или «📋 Скопировать ссылку» и отправьте её второму аккаунту.
3. Со второго аккаунта откройте ссылку → бот поздоровается и покажет карточку клиента; первому аккаунту придёт
   «👀 … открыл(а) карточку».
4. Дальше — шаги 3–9 варианта А, но клиентские кнопки нажимает второй аккаунт, а «Получил(а)», «Выполнено»
   и «Приложить чек» — первый.
5. `/deals` в любой момент — у каждого аккаунта свои разделы «Я исполнитель» / «Я клиент»: дата, название-ссылка
   на карточку, сумма и статус словом; под списком — кнопки «Пн 28 сен 14:00 · Маникюр» и «📁 Мои сделки».
6. **Правка условий** (до подтверждения): второй аккаунт — «✏️ Предложить изменения» и текст; первому приходит
   уведомление с кнопкой «✏️ Изменить условия» → мини-приложение открывается сразу на форме этой сделки → поменяйте
   дату или сумму → «Отправить новые условия». Второй аккаунт получает «Исполнитель изменил условия (версия 2):
   срок → …; сумма → …», в карточке — «Версия 2 · условия изменены …»; «✅ Подтверждаю» подтверждает версию 2.
   То же проходится одним аккаунтом в демо-сделке.
7. **Повторить** (после закрытия): «📁 Мои сделки» → «☰ Список» → «Закрытые» → «Повторить» (или «🔁 Повторить» в
   карточке) → условия подставлены, дата пустая, включено «Тот же клиент: {имя}» → «Создать и отправить клиенту».
   Карточка сразу приходит второму аккаунту — без ссылки и без пересылки.
8. **«📁 Мои сделки»** — «📅 Расписание»: лента дней, под датой — число записей, ниже записи дня по времени.

### Что стоит попробовать сломать
- Нажать «Подтверждаю» дважды → «Это уже сделано — карточка актуальна», второго события не будет.
- Оплатить картой `5555 5555 5555 4600` (недостаточно средств) → в карточке появится причина отказа

  начинается перевод. Один живой платёж на сделку и вид платежа — всегда.

- Прислать вместо чека документ `.docx` → «Нужен файл или фото», ожидание чека сохранится.

## 13. Известные ограничения

Ограничения платформы:
- **Бот не может написать первым.** `chat_id` диалога появляется только после того, как человек сам открыл бота,
  поэтому клиент обязан один раз перейти по ссылке. Если он этого не сделал, уведомления ему не уходят — это видно
  в логах как `reminder.skipped {reason:'no_chat'}`, сделка при этом живёт.
- **Клиент без установленного MAX** не теряется: ссылка `https://max.ru/<бот>?start=…` вне MAX открывает визитку
  бота с кнопкой «Открыть в браузере» (web.max.ru) — проверено вживую 21.09.
- **Бот не может создать общий чат сторон**, поэтому карточка — два сообщения (по одному у каждой стороны),
  синхронизированные по состоянию.
- **Один токен — один работающий экземпляр:** запуск в режиме `polling` удаляет webhook-подписки этого токена.
  Развёрнутый сервер восстанавливает свою подписку сторожем раз в 5 минут; `/readyz` показывает `subscription: true|false`.
  Для проверки сборки без бота — `MAX_MODE=off`.
- **Мини-приложение** привязывается к боту через форму организаторов, а не через API. До привязки весь сценарий
  проходится демо-сделкой из меню и командой `/new`.
- **Вебхук платежей требует HTTPS.** ЮKassa доставляет уведомления только на `https://` с портом 443 или 8443
  (`docs/CONTRACTS.md` §2.5), поэтому при локальном запуске на `http://localhost` уведомление не придёт
  физически. Оплата всё равно подтвердится: планировщик опрашивает статус платежа у провайдера не чаще
  раза в 60 с (`docs/SPEC.md` §10.3), и у клиента есть кнопка «🔄 Проверить оплату» — синхронный запрос
  статуса. То же касается webhook-режима самого MAX: он требует HTTPS, порт 443 и сертификат доверенного CA,
  самоподписанные не принимаются. Оба вебхука работают только на развёрнутом сервере.

Принятые риски хостинга:
- **Весь трафик идёт на `91-186-197-163.sslip.io`** — внешний публичный DNS-сервис без SLA: он превращает имя
  с IP в сам IP, домен не нужен. Сертификат Let's Encrypt на это имя действует до 20.12.2026 и продлевается Caddy
  автоматически. Если sslip.io станет недоступен, план — купить домен (`dogovorilis.online`), направить его на
  тот же IP, сменить URL вебхуков MAX и ЮKassa и адрес мини-приложения в настройках бота. Решение команды
  от 25.09: риск принят на период оценки.

Границы этой версии:
- **Т-Банк СБП не подключён** (решение команды): при `PAYMENT_PROVIDER=tbank` рейл «ссылка» работать не будет.
  Рабочие значения — `yookassa` и `none`.
- Напоминания уходят только тем, кто открыл диалог с ботом: бот не может написать первым (`docs/MAX_API.md` §1).
  Напоминание без диалога гасится с причиной `no_chat`, в журнале сделки остаётся событие `reminder.skipped`.
- Квитанция PDF: стороны, условия, подтверждения, платежи, хронология «перевёл / не вижу / получил», чек
  («содержимое не проверялось»), отмена и отметки возврата, подвал. История версий условий и QR — следующий шаг.
- В мини-приложении экраны «Новая сделка», «Готово», «Мои сделки» (расписание и список), «Сделка», «Изменить условия»,
  «Повторить сделку» и «Настройки». Экран сделки информационный: кнопок оплаты на нём нет (оплата — в карточке в чате),
  квитанция PDF отправляется в чат с ботом, а не скачивается (WebView не передаёт авторизацию при скачивании).
  Подтверждения телефона в настройках (§7.7, Should) нет.
- Адреса как отдельного поля нет — он пишется в «Уточнениях» и виден в карточке; в напоминании за 30 минут его нет.
- Рабочих часов и перерывов исполнителя нет: клиент выбирает время по сетке 08:00–21:30 (МСК), занятость считается
  только из договорённых сделок исполнителя. Настройка рабочих часов — следующий шаг (`docs/SCALING.md` §6).
- «Мои сделки» в мини-приложении берут до 200 последних сделок одним запросом и группируют по дням на телефоне;
  у пользователя с большим числом сделок самые давние в списке не появятся (в чате `/deals` — все активные).
- Утренняя сводка собирается из записей на день отправки: пришла только если на сегодня что-то есть; сводка за
  день, пропущенный из-за простоя сервера, не досылается.
- Фото/макет к сделке и загрузка файлов через API не сделаны (Should по `docs/SPEC.md` §15).

Осознанно не делаем никогда (`docs/SPEC.md` §15, Won't): приём денег на себя, автоформирование чека НПД
(публичного API «Мой налог» нет), юридически значимая подпись, возвраты через провайдера, CRM.

Известные дефекты и подводные камни, которые приходится обходить (полный список — `docs/CONTRACTS.md` §1.14):
- `@maxhub/max-bot-api` 0.3.1 падает на сообщении без текста (одно вложение — например, чек фотографией),
  если зарегистрирован `bot.command`. Обход — middleware до команд, `server/src/transport/bot/handlers/input.ts`.
- Обработчик webhook SDK (`webhookCallback()`) нельзя просто повесить на маршрут Fastify: JSON-парсер Fastify успевает
  вычитать поток запроса, и обработчик SDK ждёт тело, которого уже не будет, — в режиме `webhook` бот при этом
  молчит. Обход — отдельный плагин со своим парсером и `reply.hijack()`,
  `server/src/transport/http/routes/max-webhook.ts`, покрыт `server/test/webhook-mode.test.ts`.

## 15. Возможности MAX сверх минимума (платформенный бонус)

Одна сквозная связка, работающая от создания сделки до её закрытия:
1. **Диплинк с payload приводит второго участника.** `https://max.ru/<бот>?start=d_<id>` — единственный способ
   привести клиента: бот не может создать чат и не может написать первым. Обработчик принимает оба источника
   события (`bot_started` с payload и `message_created` с `/start d_<id>`) и идемпотентен.
2. **Мини-приложение с серверной валидацией `initData`** — авторизация без логина и пароля: HMAC-SHA256 по
   алгоритму MAX, сравнение через `timingSafeEqual`, срок `auth_date` 24 ч. Реализация — `transport/http/auth.ts`,
   алгоритм проверен отдельным тестом на примере из документации.
3. **Живая карточка** — `POST /answers` обновляет то же сообщение у нажавшего, `PUT /messages` — карточку второй
   стороны. Статус меняется на месте у обоих, без спама; короткое уведомление отправляется отдельно, потому что
   правка сообщения не даёт push.
4. **Шеринг через `https://max.ru/:share`** и **`clipboard`-кнопка** — ссылка уходит клиенту в существующий чат
   в один тап, без копирования руками; в мини-приложении — `shareMaxContent({ text, link })`, ссылка ровно одна.
5. **Мини-приложение открывается сразу на нужном экране** по `start_param` кнопки `open_app` из карточки или
   уведомления: `edit_<id>` — правка условий этой сделки, `repeat_<id>` — повтор, `deals` — расписание,
   `settings` — настройки, `new` — новая сделка. Экран, с которого открыли, — корневой: «назад» закрывает приложение.

Всё это проходится в сценарии §11 и покрыто сквозными тестами. Подробнее — `docs/SPEC.md` §16.

## 16. Собственный API

Внешнего API нет: HTTP-интерфейс `/api` — внутренний, для мини-приложения (авторизация по `initData`), `openapi.yaml` и `DATA-API.yaml`
не подаются (регламент: собственный API не обязателен).
